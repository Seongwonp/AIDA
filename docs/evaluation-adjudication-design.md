# 평가 판정 데이터를 어떻게 만드는가

> 집계 모듈(`experiment/evaluation/`)은 `Adjudication`과 `Ranking`을 **받기만
> 한다.** 그것을 누가 만드는지가 없었다. 이 문서가 그 생산 경로를 정한다.
>
> **이 기능이 끝나도 "자연 오류에서 성능을 검증했다"가 되지 않는다.**
> 생기는 것은 **판정을 기록할 길**이고, 판정 자체는 아직 개발자가 한다.

작성 2026-09-09.

## 왜 기존 재검수 화면을 그대로 못 쓰는가

| 기존 화면 | 평가에 필요한 것 |
|---|---|
| 순위와 의심 유형을 보여준다 | **가려야 한다** — 보고 판단이 휜다 |
| `hit`/`miss` 둘뿐 | **`hold`가 필요하다**(규약 7절) |
| 누락 후보 키에 좌표가 들어간다 | 재진단하면 키가 바뀐다(docs/25 R5) |
| 판정이 데이터셋 단위로 하나 | **평가마다 따로** 있어야 한다 |

그래서 제품 판정과 평가 판정을 **별도 파일에 따로 저장한다.** 기존
`verdicts.json`은 건드리지 않는다.

## 무엇을 언제 고정하는가

### 평가 묶음(snapshot)

평가를 시작할 때 **그 순간의 후보 목록을 통째로 얼린다.**

```
uploads/<dataset_id>/evaluations/<evaluation_id>/snapshot.json
```

| 담기는 것 | 왜 |
|---|---|
| `schema_version` | 모양이 바뀌면 옛 파일을 알아보려고 |
| `evaluation_id` | 같은 데이터셋에 평가가 여럿일 수 있다 |
| `dataset_id` | |
| `created_at`, `diagnosis_generated_at` | 어느 진단을 얼린 것인가 |
| `code_commit` | 만든 코드 |
| `ruler` | 어느 자로 잰 후보인가 |
| `candidates[]` | 후보 전부 — **잘리기 전** |
| `candidate_pool`, `total_in_queue` | 잘리기 전 전부(`all_candidates`)를 얼렸나, 옛 진단의 상위 N건(`review_queue`)인가 |
| `judge_budget` | 판정할 상위 N건. 있으면 두 방법 상위 N건의 합집합만 판정한다 |
| 후보별 `aida_rank` | AIDA 제품 순위. 심각도 순서와 다를 수 있다 |
| `candidate_set_hash` | 후보 집합이 바뀌었는지 대조 |
| `shuffle_seed` | 판정 순서를 섞은 씨앗 |

**재진단해도 snapshot은 안 바뀐다.** 진단 결과 파일을 덮어써도 평가는 얼린
목록을 계속 쓴다 — 판정 도중에 후보가 바뀌면 이미 내린 판정이 무엇을 가리키는지
알 수 없게 된다.

### `canonical_candidate_id` — 한 번 발급하고 보존한다

**화면을 다시 열 때 새로 만들지 않는다.** snapshot에 저장된 값을 계속 쓴다.

이름 하나가 **네 가지를 동시에** 지켜야 한다. 처음 안(`L{label_index}#{suspicion}`,
`C{순번:04d}`)은 셋을 어겼고, 그 다음 안(내용 해시 + 목록 순번)은 하나를 남겼다.

| 지켜야 할 것 | 어긴 방식 |
|---|---|
| 이미지 안에서만 유효한 번호를 구분한다 | `a.jpg`의 0번과 `b.jpg`의 0번이 **같은 이름** `L0#width`가 됐다 |
| 의심 유형을 안 드러낸다 | 이름이 그대로 가림 화면에 가서 `#width`가 **보였다** |
| 순위를 안 드러낸다 | `C0000`이 1순위임이 보였다 |
| **목록 순번에 안 기댄다** | 같은 (이미지, 라벨, 유형)이 여럿일 때 `occurrence`를 **큐 순서로** 매겨, 진단이 순서만 바꿔도 두 후보의 이름이 **서로 뒤바뀌었다** |

마지막 것이 특히 조용하다. 순서 규칙은 실제로 두 번 바뀌었고(docs/21 AN·AO),
바뀌는 순간 A에 내린 판정이 B에 붙는다. 아무 오류도 안 난다.

그래서 이름은 **후보의 내용을 요약한 값**이고, 그 내용에 **상자를 넣는다.**

```
L + sha256({image, label_index, suspicion, box})[:16]   기존 라벨
C + 같은 규칙 (label_index는 null)                      누락 후보
```

### 후보 이름과 실제 오류 이름은 다르다

**좌표는 후보 이름에는 써도 되고, `unique_error_id`에는 쓰면 안 된다.**

| | 무엇을 가리키는가 | 좌표 |
|---|---|---|
| `canonical_candidate_id` | **얼린 진단 안의 한 줄** | **쓴다** — 그 줄의 좌표가 곧 정체다 |
| `unique_error_id` | **판정된 실제 오류** | **안 쓴다** — 자가 바뀌면 좌표가 흔들려도 같은 오류다 |

묶음은 얼려 있으므로 후보의 좌표는 그 묶음 안에서 안 변한다. 반면 실제 오류는
묶음을 넘어 같은 것이어야 한다(docs/25 R5에서 판정이 사라지던 원인).

### 완전히 같은 후보가 둘이면 멈춘다

이름이 겹친다는 것은 진단이 **모든 항목이 같은 줄을 두 번 냈다**는 뜻이다.
판정자는 둘을 구분할 방법이 없다 — 하나로 접으면 판정 하나가 소리 없이
사라지고, 그냥 두면 같은 것을 두 번 센다. **얼리기를 거부하고 진단 쪽을 보게
한다.**

**누락 후보의 좌표를 영구 식별자로 쓰지 않는다.** 좌표는 **근거 데이터**이지
실제 오류의 이름이 아니다. 자가 바뀌면 예측이 흔들려 좌표도 흔들린다
(docs/25 R5에서 판정이 사라지던 원인).

## 가림 판정 — 무엇을 가리고 무엇을 못 가리는가

**"의심 유형까지 완전히 가렸다"는 사실이 아니다.** 정확히 적는다.

| | |
|---|---|
| **가린다** | 어느 방법이 추천했는지, AIDA·기준선 점수, 원래 순위, 세부 의심 유형(`width`·`scale`·`duplicate`…), 내부 진단 문구(`detail`) |
| **못 가린다** | **기존 라벨 검수인지 누락 객체 검수인지** |

못 가리는 쪽은 숨길 수가 없다 — **판정 작업 자체가 다르기 때문이다.** 기존
라벨은 "이 라벨이 틀렸는가"를 묻고, 누락은 "여기 객체가 빠졌는가"를 묻는다.
이것까지 숨기면 판정자가 무엇을 판단해야 할지 모른다. 게다가 누락 `hit`은
어느 객체인지까지 정해야 해서 화면 자체가 달라진다.

**보여주는 것**: 이미지, 기존 라벨 박스, 후보 박스, 클래스.

판정 순서는 **고정 씨앗으로 섞고 그 씨앗을 snapshot에 남긴다.** 안 남기면 같은
순서를 다시 만들 수 없다.

## `unique_error_id`를 누가 만드는가

| 판정 | 규칙 |
|---|---|
| 기존 라벨 `hit` | `{image}/L{label_index}`로 **자동 생성.** `suspicion`이 달라도 같은 라벨이면 같은 오류다 |
| **누락 객체 `hit`** | 판정자가 **"새 누락 객체"를 만들거나 이미 만든 것에 연결**한다. 화면은 `M1`·`M2`만 보내고 **이미지는 서버가 붙인다** |
| `miss`·`hold` | **만들지 않는다** |

**자동 IoU 병합을 하지 않는다.** A–B와 B–C만 겹치는 연쇄, 동점, 클래스가 다른
상자에서 답이 갈린다(docs/evaluation-methodology-sources.md 7절).

**누락 `hit`인데 어느 객체인지 안 정하면 저장을 완료하지 않는다.** 조용히 후보
id로 대신하면 겹친 후보가 서로 다른 오류로 세어져 **고유 오류 수가 부풀려진다.**

`M{n}`은 **이미지 안에서** 번호를 매기고 저장할 때 `{image}/M{n}`으로 적는다 —
다른 이미지의 `M1`과 섞이지 않게. 이미지를 **서버가 붙이는** 이유는 기존 라벨과
같다: 판정자가 다른 이미지의 이름을 달면 두 이미지의 오류가 한 오류로 세어진다.
서버가 돌려준 `{image}/M{n}` 형태도 받는다 — 화면이 저장된 판정을 그대로 다시
보내는 것이 정상 흐름이라, 서버가 돌려준 값을 서버가 거절하면 안 된다.
데이터셋 이름은 집계 모듈이 붙인다.

## 판정의 원본은 하나

같은 후보의 판정을 방법별로 복사해 두지 않는다.

```
adjudications.json   후보별 사실 (판정, unique_error_id)
snapshot.json        방법별 점수와 순서
```

내보낼 때 `experiment/evaluation/schema.py` 계약으로 바꾼다.

## 단순 불일치 기준선 — 기존 라벨은 있고, 누락은 미정이다

### 기존 라벨 (있다)

`1 − IoU(라벨, 그 라벨과 가장 많이 겹치는 예측)`. **이 한 줄이 전부다.**

진단이 후보마다 `label_iou`를 적고(`experiment/label_diagnosis.py`), 평가 묶음이
그것을 `iou_baseline` 점수로 바꾼다. 규칙이 지키는 것 둘:

- **유형을 모른다.** 같은 라벨을 `width`와 `scale`이 지목해도 점수가 같다.
  유형별로 다르게 굴면 그건 이미 단순한 규칙이 아니다.
- **겹치는 예측이 없으면 IoU 0 → 점수 1.0.** 자가 보기에 아무것도 없는 자리이고,
  기준선의 눈으로는 가장 의심스러운 라벨이다.

`label_iou`가 없는 옛 진단 결과에는 기준선 점수가 안 붙고, 그 상태로 기준선을
넣어 내보내려 하면 **막는다.** 조용히 0점을 주면 옛 결과가 기준선을 이긴다.

### 누락 후보 — **별도 층으로 분리한다** (2026-09-09 결정)

**누락 후보에는 대응하는 라벨이 없어 IoU를 계산할 대상이 없다.** 떠오르는
방법마다 다른 것을 잰다.

| 안 | 문제 |
|---|---|
| 예측 신뢰도를 점수로 | 그건 IoU 기준선이 아니라 신뢰도 기준선이다 |
| 가장 가까운 라벨과의 IoU(=0에 가까움) | 모든 누락 후보가 동점이 되어 순서가 무의미 |

**억지로 만들지 않고 층을 나눈다.**

- 주 비교는 **기존 라벨 후보만** 대상으로 한다.
- 누락 후보는 **별도 평가 층**으로 분리해 **기술 통계만** 보고한다.
- 누락 층에는 사전 정의된 비교군이 없으므로 **성공·실패를 판정하지 않는다.**
- 예측 신뢰도를 IoU 기준선과 **임의로 섞지 않는다.**
- 나중에 누락 기준선을 도입하려면 **가설·점수·동점 처리·Δ를 따로 사전
  등록**하고 검증한 뒤에 넣는다.
- 두 층의 결과를 **하나의 숫자나 하나의 전체 성공 판정으로 합치지 않는다.**

주 비교의 결과는 **"AIDA가 만든 동일 후보 집합 안에서의 조건부 재정렬 효과"**
다. 후보 생성까지 포함한 전체 제품 효과가 아니다.

## 두 방법의 순서와 판정 대상 (2026-09-13)

### AIDA 순서는 제품 순위다

평가는 AIDA를 **진단의 `rank`**로 줄 세운다. 심각도가 아니다. 제품은 계통적
유형을 먼저, 그 안에서 심각도 순으로 보여주므로(`label_diagnosis.review_order`)
두 순서가 다를 수 있고, 심각도로 줄 세우면 **제품이 안 쓰는 순서**를 평가한다.
실제로 그렇게 되어 있었다 — 검사로 재현한 뒤 고쳤다. 순위가 없거나 겹치면
내보내기를 막는다. 내보내기의 `severity`는 집계가 줄 세우는 값이라 AIDA는
`−rank`(음수)이고, 원래 점수는 `score`에 따로 둔다.

**어느 순위 버전의 `rank`인지 묶음이 얼린다 (2026-09-14,
[adr-ranking-separation.md](adr-ranking-separation.md)).** 평가를 시작할 때
`ranking_version`(기본 `aida_v1_systematic_boost`)을 받아 **그 버전의 진단 파일**을 얼리고,
파일에 적힌 버전이 다르면 얼리지 않는다. 새 묶음은 버전을 지문 재료에 넣는다. **버전이 없는
옛 묶음(prelim1)은 v1으로 읽고 지문 재료에 버전을 넣지 않아 지문이 그대로다.** 얼린 뒤 다른
버전으로 재진단해도 묶음은 바뀌지 않는다. 한 묶음에는 AIDA 순서가 **한 벌**만 있다 — v1과 v2를
같은 후보로 견주려면 두 벌을 얼리는 기능이 따로 필요하다
([next-evaluation-proposal.md](next-evaluation-proposal.md)).

### 모집단은 잘리기 전 AIDA 후보 전부다

`review_queue`는 AIDA 순위 상위 N건(기본 100)이다. 그것만 얼리면 기준선이 AIDA
하위 후보를 끌어올릴 기회가 없어 비교가 AIDA에 유리하게 휜다. 진단은
`all_candidates`를 함께 쓰고 평가는 그것을 얼린다. 옛 진단은 `review_queue`를
얼리되, 얼린 수가 `total_in_queue`보다 적거나 그 값이 없으면 **두 방법
내보내기를 막는다.**

**규칙에 안 걸린 라벨은 모집단에 없다.** 주 비교가 "AIDA 후보 안의 재정렬"이라
필요하지 않다. 후보 선정까지 포함한 전체 효과를 재려면 모집단을 전체 라벨로
넓혀야 하고, 그것은 **평가 범위 변경**으로 명시하며 추천 안 된 라벨의 처리와
동점 규칙을 먼저 정한다.

### 판정은 두 방법 상위 N건의 합집합

평가를 시작할 때 `judge_budget=N`을 주면 판정 목록에는 층마다 그 층에 정의된
방법의 상위 N건 합집합만 온다 — 기존 라벨 층은 AIDA·기준선, 누락 층은 AIDA만.
겹치는 후보는 한 번만 판정하고, 합집합 밖의 후보에는 판정을 저장하지 않는다.
상위 N건을 고르는 규칙은 집계의 동점 규칙과 같다(점수 내림차순, 이미지 이름,
후보 id). 그래서 **N 이하의 어느 검수량에서도** 두 방법 모두 판정이 빠진 후보가
없다. N보다 큰 검수량으로 집계하면 판정 안 된 후보가 예산에 들어온다 —
내보내기의 `judge_budget` 이하로만 읽는다. **N은 판정 전에 정한다.**

## 모집단과 비교 모드 (2026-09-16)

prelim1은 **AIDA가 만든 후보 안에서만** 두 순서를 견줬다. 그것으로는 "규칙이 놓친 라벨"과
"필터가 버린 예측"을 못 잰다. 그래서 묶음이 얼리는 것을 넓혔다
([next-work-2026-09-15.md](next-work-2026-09-15.md) W3).

### 후보의 출처

| `source` | 무엇 | 어디서 |
|---|---|---|
| `aida_candidate` | AIDA 규칙이 만든 후보 | 진단의 `all_candidates` |
| `label` | 규칙에 **안 걸린** 기존 라벨 | 진단의 `all_labels` |
| `unmatched_prediction` | 누락 필터가 **버린** 예측 | 진단의 `unmatched_predictions` |

**같은 대상은 한 번만 얼린다.** AIDA가 고른 라벨은 모집단에도 있지만 후보는 하나이고, 거기에
방법별 점수가 함께 붙는다. 둘로 나누면 판정자가 같은 상자를 두 번 보고 한 오류가 두 번
세어질 자리가 생긴다. 기존 라벨은 (이미지, 라벨 번호)로, 누락은 (이미지, 상자)로 잇는다 —
진단과 평가가 상자를 같은 자리에서 반올림하므로 그대로 맞는다.

**상자가 같은 미매칭 예측이 둘 이상이면 얼리기를 거부한다.** 판정 화면은 이미지와 상자만
보여주고 후보 이름에도 클래스가 없다(옛 지문과 호환되어야 해서 바꿀 수 없다). 조용히 하나를
덮어쓰면 그 후보의 확신도와 기준선 점수가 다른 예측의 것이 되고, 둘 다 만들면 판정자가
구분할 수 없는 후보가 생긴다. 다중 클래스에서 클래스별 NMS가 같은 자리에 두 상자를 낼 수
있으므로 실제로 일어날 수 있는 경우다.

**모집단이 없는 옛 진단은 아무것도 바뀌지 않는다.** 후보 이름도 그대로다.

### 방법과 모집단

| 층 | 방법 | 모집단 | 순서 |
|---|---|---|---|
| 기존 라벨 | `aida` | AIDA 후보 | 제품 순위 |
| 기존 라벨 | `iou_baseline` | AIDA 후보 | `1 − label_iou` |
| 기존 라벨 | `all_label_iou` | **모든 기존 라벨** | `1 − label_iou` |
| 누락 | `aida` | AIDA 누락 후보 | 제품 순위 |
| 누락 | `unmatched_confidence` | **필터 전 미매칭 예측 전부** | 예측 확신도 |

**자기 모집단 밖 후보는 그 방법의 순서에 없다.** 맨 뒤로 보내지 않는다 — 그러면 그 방법이
만들지도 않은 후보를 본 것처럼 세어진다.

### 예산 규칙 (판정 전에 고정한다)

- 판정 대상은 층마다 **방법별 상위 N의 합집합**이다. 겹치면 한 번만 판정한다.
- **어떤 방법의 모집단이 N보다 작으면 남는 예산은 안 쓴다.** 다른 방법의 후보로 채우지
  않는다. 그 방법이 상위 N을 채우지 못했다는 사실 자체가 결과의 일부다.
- 무작위 표본 K는 **예산과 별도로 전부 판정한다.** 표본에서 빠진 것이 생기면 그 층의 비율
  추정이 깨진다.
- 이 규칙을 사전 등록에도 같이 적는다.

### 비교 모드

| `mode` | 모집단 | 질문 |
|---|---|---|
| `within_aida_candidates` (기본) | AIDA 후보만 | 후보 안의 재정렬 — prelim1과 같은 질문 |
| `candidate_generation_included` | 규칙 밖까지 | 후보 생성까지 포함한 효과 (Q-A·Q-C) |

기본 모드는 옛 규칙 그대로다 — 후보 집합이 방법마다 다르면 거부한다. 넓은 모집단을 보는
방법(`all_label_iou`·`unmatched_confidence`)은 **후보 생성 포함 모드에서만** 쓸 수 있고, 그
모드의 내보내기는 `method_population`에 방법별 모집단 크기를 적는다.

**누락 층은 기준선이 생겨도 보조 기술 통계다.** `comparison_allowed`는 거짓이고
`descriptive_only`는 참이다 — 1차 지표로 올리려면 가설·점수·동점·Δ를 따로 사전 등록해야 한다.

### 무작위 표본

`random_sample_size` K와 `random_sample_seed`로 **규칙 밖 기존 라벨에서** K건을 뽑아 후보마다
표시한다. AIDA가 고른 후보는 표본이 아니다 — 이 층은 "규칙이 놓친 라벨에 오류가 얼마나
있나"를 재기 때문이다. 씨앗이 없으면 거부한다(같은 표본을 다시 못 만든다). 표본은 지문에
들어가고, 내보내기의 각 줄에 `source`·`random_sample`로 실린다.

**규칙은 "표본이 방법의 예산을 쓰지 않는다"이지 "표본을 순위에서 뺀다"가 아니다.**

- 표본으로 뽑힌 라벨도 `all_label_iou`의 모집단에는 그대로 있다. 거기서 빼면 **그 방법의
  순서가 표본 추출에 따라 흔들린다** — 표본은 무작위인데 순서가 그것에 좌우되면 안 된다.
- 표본은 상위 N 합집합에 **더해져** 판정될 뿐, 어느 방법의 상위 N도 바꾸지 않는다(검사로 고정).
- 표본 층의 추정(규칙 밖 라벨의 판정 오류 비율)은 **따로 낸다.** 방법별 고유 오류 수와 한
  숫자로 합치지 않는다.

## 판정자 간 불일치 — **아직 설계되지 않았다**

지금 판정은 한 사람이 한다. 두 번째 판정자를 두어도 정답이 자동으로 정해지지
않는다. 필요한 것은 공통 판정 지침, 서로의 답을 가린 독립 판정, 불일치를
조정하는 절차(누가, 무엇을 보고, 조정 전 판정을 어떻게 남기는가)다. 지금 파일
구조는 평가마다 판정 파일이 **하나**라 판정자별 원본을 따로 둘 자리가 없다.
한 사람의 반복 판정은 **일관성**을 보여줄 뿐 정확성을 입증하지 않는다.

## 저장 안전성

- 평가 파일은 **기존 `verdicts.json`과 별도**다.
- 같은 폴더 임시 파일 + `os.replace`로 원자적 저장(docs/25 R4와 같은 규칙).
- 저장 실패 시 기존 판정 보존, **500으로 알린다.**
- 깨진 파일은 **손상으로 표시**하고 빈 판정으로 위장하지 않는다.
- **snapshot의 후보 집합 해시가 안 맞으면 판정을 안 읽는다** — 다른 목록에
  붙은 판정을 되살리면 무엇을 가리키는지 알 수 없다.
- 데이터셋을 지우면 평가 파일도 같이 지운다.

**여러 탭 동시 편집은 지금 다루지 않는다.** 평가는 한 사람이 한 자리에서 하는
것으로 본다 — 제품 쪽과 같은 방침이고(docs/review-model.md), 감지도 안 한다.

## 내보내기

**기준은 JSON이고 CSV는 사람이 보려고 만드는 파생물이다.**

```
evaluation_export.json
  schema_version, evaluation_id, snapshot_hash, dataset_id,
  adjudications[]: canonical_candidate_id, image, label_index, suspicion,
                   verdict, unique_error_id, group_id, complete
  rankings[]:      method, canonical_candidate_id, severity, rank
```

`experiment/evaluation/importer.py`가 그 어댑터다. **두 세계의 유일한
연결점**이며, 빠진 것을 조용히 채우지 않고 멈춘다 — 어댑터가 기본값을 만들면
집계가 검증한 규약이 무의미해진다. 여러 평가를 합칠 때 데이터셋 이름이 겹치면
거부한다(묶음이 합쳐져 재표집이 틀린다).

**AIDA와 기준선의 후보 집합이 다르면 내보내기를 거부한다** — 정렬 효과는 같은
후보 안에서만 잰다.

**내보내기는 `ranking_version`과 `ranking_version_recorded`를 싣는다** (옛 묶음은 v1·거짓).
집계 어댑터는 버전 기록이 없는 내보내기를 v1으로 읽고, **순위 버전이 다른 내보내기를 한 집계에
합치지 않는다** — 같은 `aida`라는 이름이라도 v1과 v2는 다른 순서다. **v2 묶음은
`aida,iou_baseline`을 내보내지 않고, 집계도 그런 v2 내보내기를 읽지 않는다** — v2의 기존 라벨
순서가 기준선과 같은 신호라 견주는 뜻이 없다.

내보내기는 **층(`scope`)을 받고, 거른 것을 결과에 적는다.**

```
requested_scope        labelled_candidates | missing_candidates | all_descriptive
total_candidates       얼린 후보 전부
included_candidates    이 층에 담긴 수
excluded_candidates    뺀 수
exclusion_reasons      왜 뺐는가 (사유별 건수)
comparison_allowed     방법 간 비교에 써도 되는가
comparison_limitation  써도 되는 경우에도 무엇으로 읽어야 하는가
descriptive_only       기술 통계 전용인가
```

비교군이 없는 층(`missing_candidates`·`all_descriptive`)에 기준선을 붙여
달라고 하면 **거부한다.** 붙일 수 있게 두면 그 자체로 "견줄 수 있다"는 뜻이
되어 버린다.

## 옛 형식과의 호환

`verdicts.json`은 **제품 판정**이고 평가와 섞지 않는다. 평가는 새 파일에만
쓰고, 옛 파일을 읽지도 고치지도 않는다.

## 경로

| 무엇 | 어디 |
|---|---|
| 평가 시작(묶음 고정) | `POST /api/datasets/{id}/evaluations` (`judge_budget` 선택) |
| 가림 판정 목록 | `GET .../evaluations/{eid}/queue` |
| 판정 저장 | `PUT .../evaluations/{eid}/adjudications` |
| 집계용 내보내기 | `GET .../evaluations/{eid}/export?methods=aida&scope=labelled_candidates` |

저장 요청에는 `candidate_set_hash`를 함께 보낸다. 안 맞으면 저장하지 않는다.
