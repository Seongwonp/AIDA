# 판정자가 둘 이상일 때 — 설계 초안 (구현 안 함)

> **설계 초안이다.** 코드도 판정 자료도 없다. 둘째 판정자를 구하기 **전에** 사용자가 검토하고,
> 채택하는 부분만 사전 등록과 구현으로 옮긴다. 순서표 [next-work-2026-09-15.md](next-work-2026-09-15.md) S1.
> 외부 판정자 모집·연락은 사용자 승인 후에 한다.

## 1. 왜 필요한가

- 지금까지 판정자는 **한 사람(개발자)** 이다. 한 사람의 판정은 **일관성**을 보일 뿐 정확성을 입증하지
  않는다([evaluation-adjudication-design.md](evaluation-adjudication-design.md)).
- 다음 1차 질문(Q-A)의 결과는 **경계 사례를 어떻게 보느냐**에 민감하다 — 예를 들어 "상자가 조금 좁은
  라벨"을 오류로 볼지. prelim1에서 오류로 본 18건 중 다수가 기하 유형이었다.
- 판정자를 늘려도 **정답이 자동으로 생기지 않는다.** 필요한 것은 절차다: 공통 지침, 서로 가린 독립
  판정, 불일치를 조정하는 규칙, 조정 전 원본의 보존.

## 2. 원칙

| 원칙 | 이유 |
|---|---|
| **서로 가린 독립 판정** — 다른 판정자의 판정·기록을 볼 수 없다 | 보면 한쪽이 다른 쪽을 따라가 일치도가 부풀려진다 |
| 같은 묶음(`candidate_set_hash`)·같은 지침·같은 가림 화면 | 판정 대상이나 보이는 정보가 다르면 불일치가 판정자 차이가 아니게 된다 |
| **조정 전 원본을 지우지 않는다.** 조정은 별도 기록 | 조정이 결과를 어느 쪽으로 움직였는지 나중에 볼 수 있어야 한다 |
| 1차 지표가 **어느 판정 원본**을 쓰는지 판정 전에 등록 | 결과를 보고 유리한 원본을 고르면 사후 설명이다 |
| 판정자는 가명 코드로만 적는다 | 이름·연락처를 저장소에 넣지 않는다 |

## 3. 흐름

### 3.1 지침 보정 — 평가 데이터를 쓰지 않는다

두 판정자가 **소비된 개발 데이터**(prelim1 등)의 같은 후보 일부를 따로 판정하고, 갈린 사례를 보고
판정 지침 문장([manual-timing-pilot.md](manual-timing-pilot.md))을 보완한다. **이 보정 자료는 평가
결과에 넣지 않는다.** 보정 묶음 크기는 `[결정]`.

### 3.2 독립 판정

- 판정자마다 **판정 파일과 작업 기록이 따로**다(4절).
- **섞는 순서** `[결정]`:

  | 선택 | 장점 | 단점 |
  |---|---|---|
  | 두 판정자가 같은 순서 | 피로·학습 효과가 같은 자리에 온다 — 불일치가 순서 탓이 아니다 | 순서 효과가 두 사람에게 같이 들어가 상쇄되지 않는다 |
  | 판정자마다 다른 씨앗 | 순서 효과가 흩어진다 | 한 후보를 한 사람은 초반에, 다른 사람은 막판에 본다 |

### 3.3 일치도

두 판정이 모두 끝난 뒤, **조정 전에** 층별로 따로 적는다(기존 라벨 / 누락 / 무작위 표본).

| 적을 것 | 왜 |
|---|---|
| 둘 다 결정(hit·miss)한 후보 수, 한쪽이라도 `hold`인 수 | `hold`를 빼고 일치도를 내면 어려운 사례가 조용히 빠진다 |
| 단순 일치율 | 가장 읽기 쉽다 |
| 양성 일치(둘 다 hit) · 음성 일치(둘 다 miss)를 **따로** | 오류가 드물면 둘 다 miss인 것만으로 일치율이 높아진다 |
| 우연 보정 일치도(예: Cohen's kappa) | 우연히 맞는 몫을 뺀다. **오류 비율이 낮으면 일치율이 높아도 낮게 나온다** — 단독으로 읽지 않는다 |

**채택 전에 할 일:** 우연 보정 일치도의 계산과 해석 한계에 대한 1차 출처를
[evaluation-methodology-sources.md](evaluation-methodology-sources.md)에 먼저 적는다. 지금은 없다.

### 3.4 불일치 조정 `[결정]`

조정 대상: 한쪽 hit·다른 쪽 miss, **또는 한쪽만 `hold`**.

| 방식 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| **A. 가린 제3 판정** | 원래 두 판정을 모르는 셋째 판정자가 불일치 후보만 판정, 다수결 | 조정이 누구 편도 들지 않는다 | 판정자가 셋 필요하다 |
| **B. 합의 회의** | 두 판정자가 함께 보고 합의. 원래 판정은 그대로 둔다 | 지침의 모호함이 드러나 다음에 쓸모 있다 | 목소리 큰 쪽으로 기운다. 합의 못 한 건의 처리가 따로 필요하다 |
| **C. 조정하지 않음** | 판정자별 결과를 둘 다 보고 | 가장 투명하다 | 1차 지표가 하나로 안 나온다 — 등록 때 어느 쪽을 1차로 할지 정해야 한다 |

**누락 객체의 이름(`M{n}`)** 은 판정자마다 다르게 매겨질 수 있다. 같은 객체인지 잇는 것은 조정
단계의 일이고, **IoU로 자동 병합하지 않는다**는 기존 원칙을 그대로 지킨다.

### 3.5 집계

1차 지표는 등록한 원본(조정본 또는 판정자 한 명)으로 낸다. **민감도 분석으로 판정자별 결과를 같이
적는다** — 두 판정자에서 방향이 갈리면 그 사실이 결과의 일부다.

## 4. 저장 구조 — 구현할 때의 안

| 파일 | 무엇 |
|---|---|
| `evaluations/<id>/adjudications/<judge_code>.json` | 판정자별 판정. 지금의 `adjudications.json`과 같은 모양 |
| `evaluations/<id>/activity/<judge_code>.jsonl` | 판정자별 작업 기록 |
| `evaluations/<id>/resolution.json` | 조정 대상 후보마다 원래 판정들·조정 판정·조정 방식·조정자 코드 |

- **옛 묶음 호환:** 지금의 단일 `adjudications.json`(prelim1)은 판정자 `legacy`로 읽는다. 옛 파일을
  옮기거나 고치지 않는다.
- **가림:** 서버가 판정 화면에 **그 판정자의 판정만** 돌려준다. 다른 판정자 파일을 읽는 길을 화면에
  두지 않는다.
- **내보내기:** 어느 원본(`judge_code` / `resolution`)인지 요청에 **명시**해야 한다. 섞지 않고, 기본값을
  두지 않는다.
- 판정 저장의 지문 확인·원자적 저장·손상 표시는 지금 규칙을 판정자별 파일에 그대로 쓴다.

## 5. 사전 등록에 넣을 항목

판정자 수와 성격(개발자 / 외부), 지침 보정 묶음, 섞는 순서 방식, 일치도 지표와 층, 불일치 조정 방식,
1차 지표가 쓰는 판정 원본, 민감도 분석. [qa-preregistration-draft.md](qa-preregistration-draft.md)의
D8(판정자)이 둘 이상으로 정해지면 이 항목들이 그 초안에 들어간다.

## 6. 이 설계가 말하지 않는 것

- **두 사람이 일치해도 정답은 아니다.** 같은 지침의 같은 오해를 공유할 수 있다.
- 판정자 모집·보수·동의 같은 운영 문제는 다루지 않는다.
- 구현 비용을 재지 않았다. 판정 화면·서버·집계를 모두 건드린다.
