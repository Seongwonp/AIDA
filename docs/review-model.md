# 검수 판정의 식별과 보관 — 정의

> **2026-09-09 후속 검증:** 아래는 기존 구현의 규약과 수정 기록이다. 초기 조회·연속 저장의 경쟁, 빈 서버와 로컬 사본의 충돌, 파일 손상, 재진단 시 판정 수명은 [25번 계획 R1~R6](25-advancement-roadmap.md)에서 추가 검증한다. 정적 검토의 위험 후보를 실행 재현된 결함이나 수정 완료로 해석하지 않는다.

> docs/24 B1. "무엇을 무엇으로 식별하는가"와 "저장이 엇갈리면 누가 이기는가"를
> 코드 밖에 적어 둔다. 정의가 없으면 판정이 조용히 섞이거나 사라지는데,
> **실제로 한 번 그랬다**(아래 "고친 것" 참고).

## 무엇이 무엇을 식별하는가

| 층 | 식별자 | 바뀌면 |
|---|---|---|
| 데이터셋 | `dataset_id` (12자리 16진수) | 다른 데이터셋 |
| 진단 실행 | **식별자가 없다** | 아래 참고 |
| 후보 | `image#label_index#suspicion`, 라벨이 없으면 `#좌표`가 붙는다 | 다른 후보 |

### 순서 변경과 재진단의 구분

- **순서 변경**: 같은 후보의 `rank`만 달라진다. **키에 `rank`를 넣지 않으므로
  판정이 그대로 붙어 있다.** 순서 규칙은 실제로 두 번 바뀌었다(docs/21 AN·AO).
- **재진단**: 같은 데이터셋을 다시 진단하면 후보 목록 자체가 달라진다. 라벨을
  가리키는 후보(`label_index`가 있는 것)는 **같은 키라 판정이 이어진다.**
  누락 후보는 좌표가 조금만 달라도 다른 키가 되어 **판정이 안 이어진다.**

**진단 실행에 식별자가 없다는 것이 지금의 한계다.** 그래서 "이 판정이 어느
진단 결과에 대한 것인가"를 되짚을 수 없다. 후보 키가 우연히 같으면 다른 실행의
판정이 붙는다 — 라벨을 가리키는 후보에서는 그게 **의도한 동작**(같은 박스니까)
이지만, 그 둘을 구분할 방법은 없다. **필요해지면 그때 만든다.**

## 저장과 충돌

판정은 **두 곳**에 남는다.

| | 위치 | 목적 |
|---|---|---|
| 브라우저 | `localStorage["aida-verdicts-<id>"]` | 서버가 죽어도 검수는 이어진다 |
| 서버 | `uploads/<id>/verdicts.json` | 다른 기계에서 이어받는다 |

**규칙.**

1. 화면을 열 때 서버를 읽는다. **서버가 비어 있지 않으면 서버가 이긴다.**
   다른 기계에서 이어받는 것이 목적이기 때문이다.
2. 서버가 비어 있으면 브라우저 것을 쓴다.
3. 판정할 때마다 브라우저에 먼저 쓰고 서버에 보낸다.
4. **어느 쪽이 실패하든 검수는 막지 않되 화면에 말한다**(`saveStatusMessage`).
   실패를 삼키면 "다른 기계에서 못 이어받게 된 것"을 아무도 모른다.

**병합은 하지 않는다.** 두 곳에 서로 다른 판정이 있으면 서버가 통째로 이긴다.
같은 사람이 한 번에 한 곳에서 검수한다고 보는 것이고, **여럿이 동시에 검수하는
경우는 지금 다루지 않는다**(인증도 사용자 개념도 없다).

## 판정의 종류

| 값 | 뜻 |
|---|---|
| `hit` | 오류 맞음 |
| `miss` | 오류 아님 |
| (없음) | 아직 판정 안 함 |

### `판단 보류`를 지금 만들지 않는 이유

애매한 사례를 위한 세 번째 값을 고려했고 **지금은 안 넣는다.**

- 지금 화면의 정밀도는 `오류 맞음 ÷ 판정한 것`이다. 보류를 넣으면 분모에서
  빼야 하는데, **그 선택이 수치를 움직인다.** 근거 없이 정할 값이 아니다.
- **쓸 사람이 없다.** 애매한 사례가 실제로 얼마나 나오는지 모른다. docs/24 E
  단계(사용자 예비 평가)에서 세어 보고 정한다.
- 지금도 **판정을 지울 수 있다**(같은 값을 다시 누른다). "보류"에 가장 가까운
  동작은 이미 있다.

### 판정 변경 기록을 지금 만들지 않는 이유

누가 언제 무엇을 바꿨는지 남기려면 **사용자 개념이 필요하다.** 지금은 인증이
없어 "누가"를 기록할 수 없고, 시각만 남기면 되짚을 때 쓸모가 적다.
docs/24 B의 완료 판정은 "판정이 섞이거나 조용히 사라지지 않는 것"이지 변경
이력이 아니다.

## 고친 것 (2026-09-08)

### 1. 같은 이미지의 누락 후보가 한 키를 공유했다

누락 의심은 대응하는 라벨이 없어 `label_index`가 `null`이다. 예전 키는
`이미지#none#missing`이라 **한 장에 누락 후보가 여럿이면 전부 같은 키**였고,
하나를 판정하면 나머지도 판정된 것으로 보였다.

라벨 인덱스가 없을 때만 좌표를 덧붙여 고쳤다. **라벨을 가리키는 후보의 키는
예전 그대로**라 이미 저장된 판정이 살아난다.

### 2. 이전 형식의 "봤다"가 "오류 맞음"으로 들어왔다

예전 버전은 본 것만 배열로 저장했는데, 그것을 `hit`으로 읽고 있었다. 코드 옆
주석에는 "판정 안 함 상태로 살려 온다"고 적혀 있었지만 **코드는 그렇지
않았다.**

정밀도가 `오류 맞음 ÷ 판정한 것`이므로, 그 형식을 쓰던 사람에게는 **보기만 한
것이 전부 맞은 것으로 세어져 정밀도가 100%로 보고된다.**

진행은 살리되 판정으로는 세지 않도록 갈랐다(`loadSeen`). "안 본 것만" 필터는
둘을 합쳐 본다.

### 3. 저장 실패를 삼켰다

서버 저장 실패가 `.catch(() => {})`였다. 브라우저에 남으니 검수는 이어지지만
**다른 기계에서 못 이어받게 된 것을 아무도 몰랐다.** 실패를 화면에 표시한다.

**세 가지 모두 재현 검사를 먼저 쓰고 고쳤다.** 프론트 검사 24 → 34건.

## 고친 것 (2026-09-08, B2)

### 4. 업로드 경로가 백엔드와 진단 스크립트에서 달랐다

백엔드의 `UPLOADS_DIR`은 환경변수로 바꿀 수 있다(Docker 볼륨 등). 진단은
서브프로세스로 돌면서 **환경을 그대로 물려받는데**, 스크립트 둘이 그 값을
안 읽고 경로를 박아뒀다.

환경변수를 쓰는 순간 **백엔드는 X에 쓰고 스크립트는 Y에서 찾는다.** 진단이
죽거나, 더 나쁘게는 다른 데이터셋을 읽는다.

경로 해석을 `config.uploads_dir()` 한 곳으로 모으고 호출할 때마다 환경을
읽게 했다. **`config`에 둔 이유**는 진단 스크립트가 ultralytics를 물어서
백엔드 검사 환경에서 못 부르기 때문이다 — 규칙만 재려고 무거운 것을 끌어오지
않는다.

### 5. CSV가 화면에 걸러진 것만 나가는데 그 사실이 없었다

내려받기는 걸러진 목록을 쓴다. 유형으로 좁히거나 "안 본 것만"을 켠 채
내려받으면 일부만 나가는데, 받는 쪽은 라벨링 도구라 **빠진 줄을 "오류 아님"
으로 오해할 수 있다.** 범위를 화면과 버튼 설명에 적는다(`csvScopeNote`).

### 6. `toCsv`의 주석이 틀렸다

"누락 의심은 가리킬 라벨이 없어 좌표도 없다"고 적혀 있었는데 **누락 의심에도
좌표는 있다** — "있어야 할 자리"인 예측 박스가 들어간다. 코드는 맞게 동작했고
주석만 틀렸지만, 그 주석을 믿고 "고치면" 누락 후보를 찾아갈 수단이 사라진다.

**흐름 전체를 검사로 묶었다** — 열기 → 개별 판정 → 새로고침 → 복원 → CSV.
프론트 34 → 41건, 백엔드 150 → 155건.

## 고친 것 (2026-09-09)

### 7. 클래스를 개수로만 맞추고 의미는 안 봤다

자를 고를 때 **인덱스 개수만** 봤다 — "라벨에 0~3이 있으니 4개를 아는 자가
필요하다". 그러면 **고객의 인덱스 2가 자의 인덱스 2와 같은 뜻인지**는 아무도
확인하지 않는다.

**순서가 다르면 진단이 통째로 어긋난다.** 클래스 오기입 지목이 헛것이 되고,
적합도는 멀쩡해 보이며, **개수가 맞으니 경고도 없다.** 화면에 아무 흔적도
안 남는 종류다.

이 프로젝트에 이미 근거가 있었다 — COCO `bicycle`(자전거)과 KITTI
`Cyclist`(탄 사람)는 의미가 다르고, 그래서 COCO 실험은 `Car` 하나만 썼다
(docs/21 AI).

YOLO 라벨(.txt)에는 이름이 없고 숫자뿐이라, zip 안의 클래스 이름 파일
(`data.yaml`·`classes.txt`·`obj.names`)을 읽어 대조한다. **없으면 없다고
말한다** — "순서가 같다고 가정합니다"를 화면에 적는다. 조용히 가정하지 않는다.

세 갈래로 말한다.

| 경우 | 화면 |
|---|---|
| 이름이 같고 순서도 같다 | 아무 말 안 함 |
| 이름을 못 찾았다 | "순서가 같다고 **가정**합니다" (주의) |
| 순서가 다르다 / 모르는 이름이 있다 | 빨간 경고 |

검사 11건. 백엔드 159 → 170건.


## 고친 것 (2026-09-09, R1)

### 8. 초기 서버 조회가 신규 판정을 덮어썼다

화면이 열릴 때 `getVerdicts`를 부르고 응답이 오면 판정을 **통째로
갈아끼웠다.** 응답이 늦으면 그 사이에 내린 판정이 조용히 사라진다.

**실제 React 화면으로 재현했다** — 순수 함수로는 못 잡는다. 결함이 컴포넌트의
상태 갱신 순서에 있기 때문이다. 응답을 붙잡아 두고 판정한 뒤 옛 응답을
돌려주니 방금 내린 판정이 `undefined`가 됐다.

**고치는 중에 두 번째 결함이 나왔다.** 기다리는 동안 **지운** 판정은 서버 것이
그대로 되살아난다. 지움도 사용자가 한 일이므로 서버의 옛 상태보다 최신이다.

**고른 방식.** 초기 로딩 중 입력을 막을 수도 있었지만, **검수를 멈추게 하지
않는 쪽**이 이 제품의 기존 방침과 맞다(서버가 죽어도 검수는 이어진다). 기다리는
동안의 변경을 `judgedWhileLoading`에 들고 있다가 응답 위에 얹는다 — 추가는
값으로, **지움은 `null`로** 기록한다. 합친 결과는 브라우저와 **서버 양쪽에**
남긴다. 안 그러면 그 판정이 이 브라우저에만 남는다.

검사 6건: 늦은 응답 중 판정 / 지움 / 서버 반영 / 조회 실패 / 새로고침 복원 /
CSV 일치. 프론트 41 → 48건.

**남은 것.** 이 수정은 **초기 조회 한 번**만 다룬다. 연속 판정의 저장 요청
순서가 뒤집히는 경우(R2)는 아직 재현도 수정도 안 했다.


## 고친 것 (2026-09-09, R2)

### 9. 저장 요청의 순서가 뒤집히면 옛 상태가 이겼다

판정할 때마다 `putVerdicts`를 부르고 **기다리지 않았다.** 판정 전체를 덮어쓰는
API이므로, 두 요청이 순서 바뀌어 도착하면 **먼저 보낸 옛 상태가 나중에 도착해
최신을 지운다.** 지운 판정도 되살아났다.

**고르는 방법이 둘이었다.**

| | |
|---|---|
| 서버에 버전을 붙여 오래된 요청을 거절 | API와 파일 형식을 함께 바꿔야 한다 |
| **클라이언트가 앞 요청을 기다린 뒤 다음을 보냄** | **골랐다** |

지금 동시성의 범위가 **"한 사람이 한 자리에서"**다 — 사용자 개념도 인증도 없다.
작은 쪽으로 먼저 막는다. **중간 상태는 건너뛴다**(전체 교체 API라 보낼 이유가
없다).

### 여러 탭 — 막지 않고 알린다

직렬화는 **한 탭 안의 순서**만 지킨다. 탭이 둘이면 서로의 요청을 모르고, 나중
탭이 앞 탭의 판정을 통째로 지운다.

**잠그지 않는다.** 잠글 상대가 없고(한 사람이다), 검수를 멈추게 하는 쪽이 이
제품의 방침과 어긋난다. 대신 `storage` 이벤트로 다른 탭의 변경을 감지해
**"이 탭에서 계속 판정하면 그쪽을 덮어쓸 수 있다"**고 화면에 말한다.

`storage` 이벤트는 **다른 탭에서만** 오므로 자기 변경과 저절로 갈린다.

**남은 것.** 탭 충돌은 **감지만 하고 합치지 않는다.** 실제로 두 탭에서 검수하는
사람이 생기면 그때 합치는 규칙을 정한다.

검사 5건(흐름 2 + 직렬화 단위 3). 프론트 48 → 53건.


## 고친 것 (2026-09-09, R3)

### 10. 지운 판정이 브라우저 사본으로 되살아났다

화면은 "서버가 비었으면 브라우저 것을 쓴다"였다. 그런데 **서버가 비는 이유가
셋이고 뜻이 서로 다르다.**

| 서버 응답 | 뜻 | 브라우저 사본 |
|---|---|---|
| 판정 없음 · `updated_at` 없음 | 아직 아무것도 저장 안 됨 | **살린다** — 유일한 원본이다 |
| 판정 없음 · `updated_at` 있음 | **전부 지웠다** | **버린다** — 지운 것이 최신이다 |
| 응답 실패 | 판단할 근거가 없다 | 살린다 (검수는 이어진다) |

가운데를 구분 못 해서 **지운 판정이 되살아났다.** `updated_at`은 한 번이라도
저장하면 값이 생기므로 그것으로 갈린다 — **서버가 이미 주고 있었고 화면이 안
보고 있었다.**

**기준 원본은 서버다.** 브라우저 사본은 서버가 아무 말도 못 할 때만 원본이 된다.

**R1과 만나는 자리도 검사했다** — 서버는 "전부 지웠다"고 하는데 사용자가
기다리는 동안 새로 판정한 경우, 옛 판정은 사라지고 방금 내린 것은 남는다.

서버 쪽 계약(`updated_at`이 지운 뒤에도 남는다)도 검사로 고정했다. 화면이 그것에
기대고 있다.

검사 5건(흐름 4 + 서버 계약 2 중 신규). 프론트 53 → 58건, 백엔드 170 → 172건.

**남은 것.** 서버 파일이 **깨진 경우**는 아직 "빈 판정"과 구분되지 않는다
(docs/25 R4).


## 고친 것 (2026-09-09, R4)

### 11. 쓰기가 실패하면 있던 판정까지 사라졌다

저장이 `write_text`로 곧장 덮어쓰기였다. **여는 순간 파일이 잘리므로 쓰다
끊기면 이전 내용이 없다.** 전체 교체 API라 잃는 것이 판정 전부다.

같은 폴더에 임시 파일로 쓰고 `os.replace`로 한 번에 바꾼다 — **같은 폴더여야**
원자적이다. 실패하면 임시 파일을 치우고 **500으로 알린다.** 저장 실패를 성공으로
보고하면 화면이 "서버에 남았다"고 믿는다.

### 12. 깨진 파일이 정상적인 빈 판정으로 위장했다

깨진 파일을 빈 판정으로 돌려주고 있었다. 검수를 막지 않는다는 뜻은 맞지만,
**R3에서 화면이 "판정 없음 · `updated_at` 없음"을 "아직 저장 안 됨"으로
읽기로 했다.** 그러면 손상된 서버를 보고 브라우저 사본을 살려 덮어쓴다 —
서버가 무엇을 갖고 있었는지 모르는 채로.

`damaged` 표시를 응답에 더했다. 화면은 이것을 **응답 실패와 같이** 다룬다.

| 서버 응답 | 브라우저 사본 |
|---|---|
| 비었고 `updated_at` 없음 | 살린다 |
| 비었고 `updated_at` 있음 | 버린다 (지운 것) |
| **`damaged`** | **살린다** — 판단할 근거가 없다 |
| 응답 실패 | 살린다 |

`damaged`이면 **`updated_at`이 있어도 "지웠다"로 읽지 않는다.**

화면에도 말한다 — "서버에 있던 판정 일부가 사라졌을 수 있으니 내보낸 CSV가
있으면 대조하세요".

**원자적 교체가 순서 문제를 푼 것은 아니다.** 그건 R2의 클라이언트 직렬화가
막는다. 두 요청이 뒤집혀 도착하면 각각은 원자적으로 쓰이고 **옛 것이 이긴다.**

검사 9건(서버 5 + 화면 4). 프론트 58 → 61건, 백엔드 172 → 177건.


## 판정의 수명 — 계승과 무효화 (2026-09-09, R5)

### 무엇이 무엇을 가리키는가

| 층 | 다시 진단하면 |
|---|---|
| 데이터셋 (`dataset_id`) | **안 바뀐다.** 라벨은 업로드 시점에 고정된다 |
| 진단 실행 | **식별자가 없다.** 결과 파일을 덮어쓴다 |
| 후보 | 자가 바뀌면 **목록이 달라진다** |

### 계승 규칙

**판정은 라벨에 대한 사실이다.** "이 박스가 틀렸는가"는 어느 자로 봤든 답이
같다. 그래서 라벨을 가리키는 후보는 **계승이 맞다** — 심각도·근거·순위가 달라져도
키가 같아 판정이 그대로 붙는다.

| 경우 | 어떻게 되나 | 맞는가 |
|---|---|---|
| 같은 라벨·같은 유형, 다른 자 | 키가 같아 **계승됨** | 맞다 |
| 누락 후보, 다른 자 | 예측 좌표가 달라져 **어긋남** | 잃는다 |
| 라벨 인덱스가 바뀜 | — | **일어날 수 없다.** 라벨은 업로드에 고정 |
| 다른 데이터셋 | 키가 데이터셋별이라 안 섞임 | 맞다 |

### 무효화 — 자동으로 옮기지 않는다

누락 후보가 어긋나면 판정이 **저장소에 남은 채 화면에서만 사라진다.**
겹침(IoU ≥ 0.5)으로 짝을 찾아 옮길 수는 있고 그 함수도 만들어 뒀지만
(`carryOverVerdicts`), **자동으로 옮기지 않는다.**

- 그 규칙을 **실제 재진단에서 재본 적이 없다.**
- 잘못 옮기면 **사람이 안 본 후보에 판정이 붙는다** — docs/24 B1에서 고친 것과
  같은 종류의 사고다.

**대신 세어서 말한다**(`orphanReport`). "이전 판정 N건이 지금 목록의 후보를
가리키지 않습니다. **지워지지 않았고** 예전 목록에서는 그대로 보입니다."
그중 겹침으로 짝이 보이는 것은 몇 건인지도 알린다.

**옛 후보 목록이 없어도 된다** — 누락 후보의 좌표가 키 안에 들어 있다.

### 남은 것

- **진단 실행에 식별자가 없다.** "이 판정이 어느 자로 본 것인가"를 되짚을 수
  없다. 지금은 `ruler.json`이 **마지막 진단의 자**만 남긴다.
- **옮기기를 사람이 누르는 길이 없다.** 세어서 말하기만 한다.

검사 15건(수명 규칙 11 + 화면 2 + 서버 2). 프론트 61 → 81건, 백엔드 177 → 179건.


## 고친 것 (2026-09-09, R6)

### 13. 저장에 실패하면 다시 시도할 길이 없었다

실패를 화면에 말하기는 했지만(B1) **다시 보낼 방법이 없었다.**

전체 교체 API라 **다음 판정이 있으면 저절로 복구된다** — 그때 전체 상태를 다시
보내기 때문이다. 문제는 **판정을 멈춘 채 끝내는 경우**다. 마지막 몇 건이
브라우저에만 남고 다른 기계에서는 영영 안 보인다.

실패 안내에 "다시 시도"를 붙였다. 누르면 지금 상태를 통째로 보낸다.

흐름 전체를 한 검사로 이었다 — 열기 → 연속 판정 → 저장 실패 → 재시도 →
새로고침 → CSV. **조각이 다 맞아도 이어 붙이면 어긋나는 자리가 있다.**

프론트 81 → 84건.
