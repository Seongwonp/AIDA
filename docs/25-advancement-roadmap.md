이 문서는 [24번 계획](24-development-plan.md)의 후속 실행 계획이다. 기존 산출물은 보존하되 A·B·C 완료를 제품 신뢰성이나 독립 검증 완료로 해석하지 않는다. 작업 우선순위와 단계 통과 기준은 이 문서를 따른다.

## 목표와 현재 판단

**같은 실제 검수 시간에 단순한 방법보다 더 많은 고유 라벨 오류를 찾고, 그 판정을 잃지 않는 도구를 만든다.**

현재는 근거와 실패 기록이 있는 연구 프로토타입이다. 자연 발생 오류, 외부 사용자 효과, 실제 시간 절감은 미검증이다. 합성 오류 성능과 테스트 통과를 이 세 가지의 증거로 쓰지 않는다.

2026-09-09 정적 검토에서 저장 요청의 순서 역전, 초기 조회에 의한 신규 판정 덮어쓰기 가능성을 발견했다. 실행 재현 전까지는 위험 후보로 취급한다. 프론트 테스트는 순수 함수 중심이므로 실제 화면의 비동기 흐름을 별도로 확인해야 한다. 기존 277건은 문서에 기록된 수이며 이번 검토 환경에서는 재실행하지 못했다.

## 1. 판정을 믿을 수 있게 만들기

- [x] **R1 초기 조회 경쟁 — 재현되어 수정.** 응답을 늦춘 뒤 판정하니 **신규 판정이 사라졌다**(`expected undefined to be 'hit'`). 이어서 **두 번째 결함**도 나왔다 — 기다리는 동안 **지운** 판정이 서버 것으로 되살아난다. 초기 로딩 중 입력을 막는 대신, 기다리는 동안의 변경(추가·지움)을 따로 들고 있다가 응답 위에 얹는 방식을 골랐다. **검수를 멈추게 하지 않는 쪽**이 이 제품의 기존 방침(서버가 죽어도 검수는 이어진다)과 맞다. 합친 결과는 서버에도 올린다. 검사 `frontend/src/components/ReviewQueue.race.test.tsx` 6건.
- [x] **R2 저장 순서 — 재현되어 수정.** 연속 판정 뒤 도착 순서를 뒤집으니 **옛 상태가 최신을 지웠고**, 지운 판정도 되살아났다. 서버 버전 검사 대신 **클라이언트 직렬화**를 골랐다 — 지금 동시성의 범위가 "한 사람이 한 자리에서"이고(사용자 개념·인증 없음) 버전 검사는 API와 파일 형식을 함께 바꿔야 한다. 앞 요청이 끝난 뒤 다음을 보내고, **기다리는 동안 쌓인 중간 상태는 건너뛴다**(전체 교체 API라 보낼 이유가 없다). **여러 탭은 막지 않고 알린다** — `storage` 이벤트로 다른 탭의 변경을 감지해 "덮어쓸 수 있다"고 경고한다. 검사 `ReviewQueue.order.test.tsx` 2건 + `makeVerdictSender` 단위 3건. **고치기 전에 정확히 2건이 실패하는 것을 확인했다.**

- [x] **R4 파일 저장 — 재현되어 수정.** 둘 다 나왔다. (1) **쓰기가 실패하면 있던 판정까지 사라졌다** — `write_text`가 여는 순간 파일을 자른다. 같은 폴더 임시 파일 + `os.replace`로 바꾸고, 실패하면 임시 파일을 치운 뒤 **500으로 알린다**(저장 실패를 성공으로 보고하면 화면이 "서버에 남았다"고 믿는다). (2) **깨진 파일이 정상적인 빈 판정으로 위장했다** — R3가 "판정 없음 · `updated_at` 없음"을 "아직 저장 안 됨"으로 읽으므로, 손상을 그대로 두면 서버 상태를 모르는 채 브라우저 사본으로 덮어쓴다. `damaged` 표시를 더해 **응답 실패와 같이 다루고**(사본 유지) 화면에 말한다. **순서 문제가 이걸로 해결된 것은 아니다** — 그건 R2의 클라이언트 직렬화가 막는다. 검사 9건(서버 5 + 화면 4).

기준선을 나중에 넣으려면 가설·점수·동점·Δ를 따로 사전 등록한다.

- **정답:** 데이터별 라벨링 지침, 보류, 판정 불일치 처리, 누락 객체 식별을 정한다. 겹친 박스의 IoU만으로 실제로 다른 두 객체를 합치지 않는다.

**여기 "완료"는 완료 *조건*이었는데 완료 *선언*처럼 읽혔다.** 본문은 N·Δ가
`TBD`라고 하면서 이 줄은 "고정되어 있다"고 적혀 있었다 — 아래 표로 갈라 적는다.

| 항목 | 상태 |

| 활동 시간 계측(중복 방지·완전성 판정·종료 시 보존) | **완료** |

절차는 [pilot-evaluation-plan.md](pilot-evaluation-plan.md)에 있다.

라이선스는 실제 데이터 선택 시 원문으로 확인한다.

## 3. 독립 데이터에서 가치 확인

처음부터 여러 대형 데이터셋을 받지 않는다. 작은 미사용 묶음으로 파이프라인과 소요 시간을 확인하고, 보존해 둔 최종 묶음으로 확정 평가한다.

- [ ] **합성 오류:** 미사용 이미지에서 혼합 오류·저오류·분포 차이를 포함한다. 기존 KITTI·COCO 개발 결과와 별도로 보고한다.
- [ ] **자연 오류:** 추천 표본과 추천 밖 표본을 출처를 가려 판정한다. 표본 추출 확률과 단위를 기록하고 전체 오류 수·재현율을 근거 없이 추정하지 않는다.
- [ ] 모델 적합성, 객체 크기, 클래스, 오류 유형별 이득·손해를 분리한다.
- [ ] `order_risk`의 실패 포착과 헛경고를 측정한다. 경고가 없다는 이유로 안전하다고 표시하지 않는다.
- [ ] 추론 대기 시간, 검수량, 중복 후보, 보류율을 함께 보고한다.

결정: 단순 기준을 이기면 4·5단계로 진행한다. 특정 유형만 이기면 지원 범위를 좁힌다. 이득이 불확실하면 제품 효능 주장을 보류한다. 자연 오류를 확보하지 못하면 합성 평가 보고서까지만 완료한다.

## 4. 결과에 따라 하나만 고도화

| 확인된 병목 | 개선 후보 | 필수 비교 |
|---|---|---|
| 모델이 객체를 못 찾음 | 모델 선택·지원 클래스/도메인 제한 | 기존 모델, 단순 모델 선택 규칙 |
| 후보는 있지만 순서가 나쁨 | 소량 사람 판정으로 순위 보정 | 현재 AIDA, 유형별 단순 보정 |
| 경고가 실패를 잘 구분함 | 추천 보류·무작위 검수 혼합 | 항상 추천, 고정 비율 무작위 혼합 |
| 중복·헛추천이 많음 | 후보 병합·추천량 조절 | 원래 후보, 단순 중복 제거 |
| 추천은 맞지만 작업이 느림 | 이미지 단위 묶기·단축키·라벨 도구 연계 | 기존 화면의 동일 시간 검수 |

보정에 쓴 사람 판정·시간도 비용에 포함한다. 개선 개발에 사용한 데이터는 최종 평가에서 제외한다. 사전 정의한 개선안과 제한된 탐색 예산을 넘기면 중단하고 원인을 기록한다. 추가 가치가 없으면 단순한 기존 방법을 유지한다.

라벨 수정 후 재학습 효과는 검수 가치가 확인된 뒤 선택적으로 평가한다. 같은 수정 예산과 별도 깨끗한 테스트셋을 사용하며, 기존 이미지 폐기형 자기 정제를 반복 확대하지 않는다.

## 5. 사람이 실제로 더 잘 검수하는가

- [ ] 개발자 자체 예비 평가로 시간 측정·기록지·판정 지침을 먼저 확인한다. **계측 계약과 도구는 준비됐다**([pilot-evaluation-plan.md](pilot-evaluation-plan.md), `experiment/evaluation/activity.py`)이고 **사람이 직접 판정할 절차도 준비됐다**([manual-timing-pilot.md](manual-timing-pilot.md), `experiment/make_timing_pilot.py`) — **진행 상태는 [HANDOFF_2026-09-10.md](HANDOFF_2026-09-10.md), 다음 작업의 규약은 [sustained-pilot-protocol.md](sustained-pilot-protocol.md)에 있다.** timing4가 실제 진단 후보로 형식 요건을 처음 충족했으나 **지속 판정 자료가 없어 N은 여전히 미정**이다. **timing1은 보조받은 리허설이라 N 산정에서 제외한다** — 판정자가 외부 도구에 도움을 받았고, 그 시간은 판정 탭에 안 잡힌다. 도움 없이 하는 timing2를 준비해 두었다. **실제 사람 판정은 아직이다.** 자동 클릭 시간은 사람의 검수 시간이 아니고, 코드가 그런 기록을 `implausible_for_human_judging`으로 막는다. 파일럿 자료는 **개발 데이터의 실제 이미지**에 오류를 주입해 만든다 — 첫 판은 빈 회색 이미지에 난수 박스여서 판정 자체가 불가능했다.
- [ ] 외부 참여자 3~5명은 **사용성 문제 탐색의 예상 규모**로만 둔다. 일반적 효과를 입증하는 표본 수로 취급하지 않는다.
- [ ] 기억 효과를 줄이도록 서로 다른 데이터 묶음과 사용 순서를 균형 배치한다.
- [ ] 활동 시간과 대기 시간을 나누고 고유 오류·보류·수정·저장 실패를 기록한다.
- [ ] 추천을 모르는 판정자의 재검토 또는 불일치 조정 절차를 적용한다.
- [ ] 참여자별 결과를 보존하고 클릭 수만으로 시간 절감을 주장하지 않는다.

완료: 사용성 문제와 알고리즘 실패가 분리되고 실제 시간당 성과를 보고할 수 있다. 참여자가 없으면 자체 평가로 표시하고 외부 효과 검증은 미완료로 둔다. 외부 연락은 사용자 승인 후 한다.

## 6. 검증된 범위만 배포하고 정리

- [ ] 작은 예제·가중치 출처·실행 명령·지원 범위·실패 사례를 묶는다.
- [ ] 다른 환경에서 설치 → 진단 → 저장 → 복원 → 내보내기를 확인한다.
- [ ] 외부 서비스가 필요할 때 인증·데이터 격리·삭제·작업 취소·자원 제한을 구현한다. 여러 사용자나 작업이 필요할 때 DB·작업 큐를 도입한다.
- [ ] 결과 보고서에 독립 성능, 사용자 효과, 비용, 한계, 미검증 항목을 구분한다.
- [ ] 대회 당시 기여와 이후 개인 개발을 근거와 함께 분리한다.

효과가 제한적이면 특정 도메인의 로컬 검수 도구 또는 재현 가능한 연구 산출물로 마무리한다. 범용 서비스 출시를 의무 목표로 두지 않는다.

## 비용과 진행 관리

기본은 기존 로컬 자원이다. 학습·추론은 시간·전력·저장공간을 사용하므로 0원이라는 표현만으로 무제한 실행하지 않는다. 장시간 GPU 작업, 대용량 다운로드, 유료 서비스는 방법·예상 시간·용량·금액 상한을 제시한 뒤 사용자 확인을 받는다. 작은 코드 테스트와 문서 정리는 바로 진행한다.

매주 기록할 것은 닫은 질문, 새 근거, 남은 위험, 다음 작업 하나다. 테스트 수·문서량·실험 횟수를 진척의 대리 지표로 삼지 않는다. 완료 표시는 재현 결과와 산출물 링크가 있을 때만 한다.
