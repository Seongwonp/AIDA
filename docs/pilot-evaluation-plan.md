# 예비 평가 운영 설계 — 시간 계측과 N·Δ 결정 절차

> **이 문서는 숫자를 정하지 않는다.** 정하는 것은 **절차**다.
>
> N과 Δ를 지금 적으면 근거 없는 값이 기준이 되고, 나중에 결과를 보고 고치면
> 그건 기준이 아니라 사후 설명이다(docs/evaluation-methodology-sources.md 4절).
> 그래서 **무엇을 재고 어떻게 계산할지**만 결과 열람 전에 못 박는다.
>
> 작성 2026-09-09.

## 왜 시간을 재는가

주지표는 "예산 N건을 검수해 고유 오류를 몇 개 찾았는가"다. 그런데 **N을 정하려면
후보 하나에 사람이 얼마나 걸리는지 알아야 한다.** 시간 상한이 있고 데이터셋이
여럿이면 N은 그 나눗셈의 결과이지 고르는 값이 아니다.

**"페이지를 열어 둔 시간"을 검수 시간으로 쓰지 않는다.** 탭을 열어 두고 점심을
먹으면 검수가 느린 것처럼 보이고, 반대로 화면을 미리 띄워 두고 재면 빨라 보인다.
둘 다 사람이 실제로 쓴 시간이 아니다.

## 시간의 종류 — 일곱을 갈라 잰다

| 이름 | 무엇 | 왜 갈라야 하는가 |
|---|---|---|
| `wall` | 화면을 연 뒤 닫을 때까지 | 전체 소요. **검수 시간이 아니다** |
| `active` | 탭이 보이고 포커스가 있으며 입력이 끊기지 않은 구간 | 사람이 실제로 쓴 시간 |
| `idle` | 마지막 입력 뒤 문턱을 넘긴 구간 | 자리를 비운 시간이 검수 시간에 섞이면 안 된다 |
| `wait` | 서버·모델을 기다린 구간 | **기계가 느린 것과 사람이 느린 것은 다른 문제다** |
| `adjudication` | 후보를 보고 판정한 활동 시간 | N 계산의 분모 |
| `missing_link` | 누락 객체를 만들거나 이미 만든 것에 연결한 시간 | 이 작업만 유독 오래 걸릴 수 있고, 그러면 누락 층의 비용이 따로 잡힌다 |
| `save_retry` | 저장 실패와 재시도에 든 시간 | **도구 결함이지 검수 비용이 아니다.** 섞으면 우리 버그가 "검수가 오래 걸린다"로 보고된다 |

`adjudication`과 `missing_link`는 `active`의 부분집합이다. `save_retry`는
`active`에서 **뺀다**.

### idle 문턱 — **결과를 보기 전에 정한다**

```
IDLE_THRESHOLD_SECONDS = 60
```

마지막 입력 뒤 60초를 넘긴 구간은 `active`에서 뺀다. 넘긴 구간 **전체**를 빼는
것이 아니라 **문턱까지는 남기고 그 뒤를 뺀다** — 후보를 60초 넘게 들여다보는
일은 실제로 있고, 그걸 통째로 0으로 만들면 어려운 후보가 공짜가 된다.

60초를 고른 근거는 **약하다.** 박스 하나를 보고 판단하는 데 1분을 넘기면 그건
보통 화면을 떠난 것이라는 짐작이다. 실측 근거가 없으므로, 예비 평가에서 이
값을 바꾸려면 **왜 바꾸는지와 바꾸기 전후 수치를 함께** 이 문서에 적는다.
**결과를 본 뒤 유리한 쪽으로 고르지 않는다.**

## 무엇을 기록하는가

평가마다 **별도 파일**에 남긴다. `snapshot.json`·`adjudications.json`·
`verdicts.json`과 섞지 않는다 — 판정 결과와 작업 기록은 수명도 쓰임도 다르다.

```
uploads/<dataset_id>/evaluations/<evaluation_id>/activity.jsonl
```

한 줄에 이벤트 하나(JSON Lines). 이어붙이기만 하므로 중간이 깨져도 앞부분이
남는다.

| 이벤트 | 언제 |
|---|---|
| `session_started` / `session_ended` | 화면을 열고 닫을 때 |
| `candidate_opened` | 후보를 화면에 띄울 때 |
| `verdict_set` / `verdict_cleared` | 판정하거나 취소할 때 |
| `missing_object_created` / `missing_object_linked` | 누락 객체를 만들거나 이을 때 |
| `moved_previous` / `moved_next` | 후보 사이를 옮길 때 |
| `save_started` / `save_succeeded` / `save_failed` / `save_retried` | 저장 흐름 |
| `visibility_changed` | 탭이 보이거나 숨을 때 |
| `focus_changed` | 창이 포커스를 얻거나 잃을 때 |

`queue_load_started` / `queue_load_succeeded` / `queue_load_failed`도 남긴다 —
**목록을 기다린 시간은 사람이 판정한 시간이 아니다.**

### 이벤트마다 담기는 것

| 항목 | 왜 |
|---|---|
| `event_schema_version` | 모양이 바뀌면 옛 파일을 알아보려고 |
| `event_id` | **이벤트마다 영구히 고유.** 재전송해도 안 바뀐다 |
| `evaluation_id` | 어느 평가의 기록인가 |
| `candidate_set_hash` | **어느 묶음에 붙은 기록인가.** 안 맞으면 다른 후보 목록의 시간이다 |
| `session_id` | 새로고침하면 새 세션이다 |
| `sequence` | 세션 안에서 0부터 하나씩. **구멍은 전송 유실을 뜻한다** |
| `canonical_candidate_id` | 어느 후보인가. 후보와 무관한 이벤트는 `null` |
| `at` | UTC 벽시계 시각 |
| `elapsed_ms` | **세션 안에서만 유효한 단조 증가 시간** |
| `meta` | 그 이벤트에만 필요한 최소한 |

### 잃지 않기

**기록이 유실되면 그 시간은 영영 없다.** 판정은 다시 누를 수 있지만 "언제
눌렀는가"는 다시 만들 수 없다.

- **창이 닫힐 때**는 `pagehide`에서 `sendBeacon`으로 넘긴다. 보통의 요청은
  브라우저가 페이지를 버리면서 같이 버린다.
- **탭이 숨을 때**도 바로 보낸다 — 모바일은 여기서 페이지를 버린다.
- 보내지 못한 것은 **브라우저에 남겨** 다음 접속 때 **같은 `event_id`로** 다시
  보낸다. 저장 자리는 `dataset_id`와 `evaluation_id`로 나눈다 — 한 자리에
  모으면 다른 평가의 이벤트가 섞여 묶음 해시가 안 맞아 통째로 거부당한다.
- **서버가 확인해 준 것만** 큐에서 지운다. 응답을 못 받았는데 지우면 그 시간이
  사라지고, 서버가 이미 저장했는데 다시 보내면 `event_id`로 걸러진다.

### 서버가 막는 것

- 아는 이벤트 이름만 받는다. 오타 하나가 조용히 들어가면 그 구간이 무엇이었는지
  알 수 없다.
- 이벤트별 필수 `meta`를 확인한다(`visible`·`focused`·`verdict`).
- 얼린 목록에 없는 후보를 거부한다.
- `elapsed_ms`·`sequence`·`session_id`·`event_id`·`at`의 형식과 `meta`·요청
  크기를 본다.
- **한 건이 틀리면 요청 전체를 거부한다.** 일부만 저장하면 기록에 구멍이 남는데
  화면은 성공으로 알고 다시 안 보낸다.
- 이미 받은 `event_id`는 다시 넣지 않고 `deduplicated` 수를 응답한다.

**벽시계와 단조 시계를 둘 다 남긴다.** 벽시계는 언제 일어난 일인지 말하지만
자정을 넘거나 시스템 시계가 바뀌면 **뒤로 갈 수 있다.** 시간 길이는 단조
시계(`performance.now()`)로만 잰다.

### 화면에 하지 않는 것

- **판정 결과를 요약해 보여주지 않는다.** 정밀도가 뜨면 판정자가 그걸 보고
  다음 판정을 조절한다.
- **시간을 화면에 띄우지 않는다.** 재고 있다는 걸 보면 서두른다.
- **버튼을 미는 것이 생기지 않게 한다.** 나타났다 사라지는 표시가 판정 버튼
  위에 있으면 연달아 누를 때 엉뚱한 버튼이 눌린다(docs/21 BC에서 실제로 겪음).

## 계산 — `experiment/evaluation/activity.py`

원시 이벤트만 저장하고 **계산은 나중에 따로 한다.** 화면이 요약을 만들면 그
숫자가 화면에 뜨기 쉽고, 규칙을 고칠 때 이미 저장된 기록을 다시 계산할 수 없다.

내는 값:

```
wall_seconds                 전체 소요
active_seconds               사람이 실제로 쓴 시간
wait_seconds                 서버를 기다린 시간
save_retry_seconds           저장 실패·재시도에 든 시간
per_candidate[]              후보별 active 시간
judged_candidates            판정을 끝낸 후보 수 (보류 포함)
median_seconds_per_candidate
p75_seconds_per_candidate    N 계산에 쓰는 값
holds, hold_rate
missing_link_seconds         누락 객체 연결에 든 시간 (별도)
save_failures, save_retries
sessions                     중단 후 재개한 횟수
```

**보류도 작업한 후보로 센다** — 사람이 시간을 썼다. **판정을 바꿔도 후보 하나로
센다** — 같은 후보를 두 번 세면 후보당 시간이 줄어 N이 부풀려진다.

### 기록이 온전한가 — 요약이 스스로 말한다

```
complete_sessions     시작과 끝이 다 있고 순번에 구멍·겹침이 없는 세션
incomplete_sessions   그렇지 않은 세션
invalid_sessions      그 세션들의 이름
duplicate_events      같은 event_id가 두 번 온 건수
missing_sequences     빠진 순번의 개수
timing_usable         이 기록으로 시간을 재도 되는가
```

**시간 통계는 온전한 세션에서만 낸다.** 브라우저가 죽으면 마지막 후보의 시간이
잘린 채 남는데, 그걸 그대로 넣으면 후보당 시간이 짧아지고 N이 부풀려진다.

`adjudication_seconds`는 **후보에 붙은 시간에서만** `missing_link`를 뺀 값이다.
예전에는 `active - missing_link`였는데, 그러면 첫 후보가 뜨기 전의 시간까지
"판정 시간"에 들어갔다 — 이름이 가리키는 것보다 넓은 값이었다. 후보에 안 붙은
시간은 `unattributed_seconds`로 따로 적는다.

## N 결정 공식 — **입력값이 아직 없다**

최종 평가의 데이터셋 수를 `D`, 사람이 쓸 수 있는 전체 활동 시간 상한을 `T`초라
할 때:

```
N = floor((T / D) / s_plan)
```

### `s_plan`이 무엇인가 — **P75가 아니다**

> **2026-09-09 정정.** 처음에는 "평균으로 잡으면 절반의 경우 상한을 넘는다"고
> 적고 P75를 계획값으로 썼다. **그 설명은 성립하지 않는다.** N건을 다 보는 데
> 걸리는 **총** 시간은 개별 후보의 P75가 아니라 **평균과 분산, 그리고 세션 간
> 상관**에 좌우된다. 후보당 P75로 나눈다고 총 시간이 상한 안에 들 확률이
> 보장되지는 않는다.

| 값 | 무엇인가 | 어디에 쓰나 |
|---|---|---|
| `mean` | 후보당 평균 활동 시간 | 총 시간의 기대값을 잡는 기준 |
| `p75` | **후보 난이도 분포의 기술 통계** | 어려운 후보가 얼마나 오래 걸리는지 보는 용도. **N의 근거가 아니다** |
| `s_plan` | **평균의 부트스트랩 95% 상한** (세션 단위 재표집) | N 계획값 |

`s_plan`도 **확률 보장이 아니다.** 부트스트랩이 가정하는 것은 "앞으로의 세션이
관측한 세션들과 같은 분포에서 온다"인데, 예비 평가 세션 몇 개로 그것을 확인할
수 없다. **보수적인 참고값**으로만 쓴다.

재표집 단위를 **세션**으로 잡는 이유는 한 사람이 한 자리에서 연달아 판정한
시간들이 서로 닮아 있기 때문이다. 후보 단위로 뽑으면 그것들이 독립인 척하게
되어 구간이 실제보다 좁아진다(docs/evaluation-methodology-sources.md 3절).

### 표본이 모자라면 계산하지 않는다

`timing_usable`이 거짓이면 `insufficient_pilot_data`를 돌려주고 **N을 만들지
않는다.** 최소 기준은 **온전한 세션 2개, 판정 후보 10건**이다.

**이 최소 기준은 근거가 약한 운영 기준이다.** 통계적으로 유도한 값이 아니라
"이보다 적으면 평균의 구간이 아무것도 말하지 않는다"는 짐작이다.

적용 전에 세 가지를 확인한다.

1. **각 데이터셋에 기존 라벨 후보가 N개 이상 있는가.** 모자라면 그 데이터셋은
   N을 못 채우고, 데이터셋 동등 가중이 깨진다.
2. **N이 너무 작아 부트스트랩이 무의미해지지 않는가.** 묶음 단위로 재표집하는데
   묶음이 몇 개 안 되면 구간이 사실상 아무것도 말하지 않는다.
3. **총 검수량이 `D × N`인가.** 규약이 그렇게 적어 두었다 — 전체를 N으로 나눠
   쓰면 작은 데이터셋에서 볼 것이 거의 없어져 동등 가중의 뜻이 사라진다.

| 필요한 입력 | 지금 |
|---|---|
| `D` (최종 데이터셋 수) | **미정** — 독립 데이터를 아직 안 골랐다 |
| `T` (전체 활동 시간 상한) | **미정** — 사용자가 정한다 |
| `s_plan` (후보당 평균의 보수적 상한) | **미측정** — [수동 파일럿](manual-timing-pilot.md)에서 나온다 |

**세 값이 모두 나온 뒤 이 공식으로 계산하고, 최종 결과를 열기 전에 별도
커밋으로 고정한다.**

## Δ 결정 절차 — **관측값을 보고 정하지 않는다**

Δ는 "이만큼 더 찾아야 쓸모 있다"는 **사업적 최소 기준**이다. 예비 평가에서
관측한 AIDA의 성능 차이를 보고 정하면, 그건 기준이 아니라 결과에 맞춘 설명이 된다.

그래서 **결과와 무관하게** 선택지를 먼저 늘어놓는다.

| 안 | 뜻 | N=100일 때 | N=200일 때 |
|---|---|---|---|
| **A** | 데이터셋마다 고유 오류 **1건** 더 | +1 | +1 |
| **B** | `ceil(0.05 × N)` | +5 | +10 |
| **C** | `ceil(0.10 × N)` | +10 | +20 |
| **D** | ROI 환산 최소 기준 | 아래 | 아래 |

> **위 숫자는 추정 예시다.** N이 아직 미정이라 100·200은 계산을 보여주려고
> 넣은 값이고, 실제 N이 정해지면 다시 계산한다.

### 각 안이 뜻하는 것

- **A**는 가장 약한 기준이다. 넘기기 쉽지만, 데이터셋마다 오류 하나 더 찾는
  것이 검수 시간을 들일 이유가 되는지는 별개 질문이다.
- **B·C**는 N에 비례한다. N이 커지면 요구도 커져 "많이 보면 많이 찾는다"는
  당연한 효과를 성과로 세지 않는다.
- **D**는 사업 쪽에서 온다: 오류 하나를 놓쳤을 때의 비용과 후보 하나를
  검수하는 비용이 있어야 계산된다. **둘 다 아직 값이 없다.**

### ROI 환산 (추정 예시)

후보당 검수 시간을 `s`초, 검수 인건비를 시간당 `w`원, 오류 하나를 놓쳤을 때의
비용을 `c`원이라 하면, N건 검수의 비용은 `N × s × w / 3600`이고 손익 분기는:

```
Δ_min = (N × s × w / 3600) / c
```

**`w`와 `c`는 이 저장소에 없다.** 사용자가 사업 기준으로 정해야 한다. 여기
적은 식은 "무엇을 알아야 Δ를 정할 수 있는가"를 보이려는 것이지 값이 아니다.

### 고정 절차

1. 예비 평가로 `s`(P75)를 잰다.
2. 사용자가 `D`와 `T`를 정한다 → `N`이 나온다.
3. 사용자가 위 표에서 Δ를 **고른다.** 근거를 함께 적는다.
4. **최종 평가 결과를 열기 전에 별도 커밋으로 고정한다.**
5. 그 커밋 이후에만 독립 데이터 확보와 예비 효과 평가로 들어간다.

## 개발용 dry pilot — 무엇이 아닌가

시간 계측과 화면 결함을 확인하려고 개발 데이터로 10~20건을 판정한다.

**하지 않는 것:**

- AIDA와 기준선 중 누가 이겼는지 계산
- 짝지은 차이나 신뢰구간 열람
- dry pilot 데이터를 최종 평가에 재사용
- dry pilot 결과로 Δ 선택
- 이것을 "자연 오류 검증"이라고 부르는 것

**확인하는 것:** 이벤트가 저장되는가, 새로고침 후 이어지는가, hit·miss·hold가
남는가, 누락 객체를 만들고 이을 수 있는가, 저장 실패와 재시도가 기록되는가,
내보내기와 시간 요약이 만들어지는가.

### 1차 dry pilot (2026-09-09) — **계측 결함 둘을 잡았다**

임시 데이터셋(후보 14개, 그중 누락 3개)으로 브라우저에서 돌렸다. 흐름은 전부
동작했고, **요약 숫자가 두 군데서 틀렸다.**

| 나온 값 | 무엇이 틀렸나 |
|---|---|
| `missing_link_seconds = 0.0` | 누락 객체를 실제로 만들었는데 0이었다. **만든 뒤의 간격**을 세고 있었고, 그 간격은 곧바로 저장이 나가서 늘 기다림에 먹혔다. 어느 객체인지 **고르는** 시간은 그 이벤트로 **끝나는** 구간이다 |
| `sessions = 4` | 페이지를 두 번 열었는데 4로 나왔다. effect마다 새 세션을 시작해서, 개발 모드의 StrictMode가 effect를 두 번 돌리면 두 배가 된다 |

둘 다 **검사가 통과한 채로 틀려 있었다** — 첫 검사가 "만든 뒤"를 정답으로
적어 두었고, 세션 수는 브라우저에서만 드러났다. 고친 뒤 2차에서
`missing_link_seconds = 3.9`, `sessions = 1`로 바뀌었다.

**이 숫자를 사람의 검수 시간으로 쓰지 않는다.** 자동 클릭이라 후보당 2~4초가
나왔고, 그 값으로 N을 계산하면 868 같은 값이 된다 — 사람이 클릭 속도로
검수한다고 가정하는 셈이다. **계획값은 사람이 직접 판정해야 나온다.**

## 남은 위험

- **판정자가 개발자다.** 자기가 만든 도구를 자기가 쓰면 막히는 자리를 그냥
  넘어간다 — 그래서 dry pilot은 **사용성 확인**이지 시간의 대표값이 아니다.
- **세션은 독립 표본이 아니다.** 같은 사람이 같은 날 연달아 한 작업이라 뒤
  세션은 앞에 익숙해진 상태다. 부트스트랩이 가정하는 독립성이 여기서 이미
  깨져 있고, `s_plan`은 그래서 **운영시간 계획용 휴리스틱**이다.
- **P75 하나로 N을 정한다.** 데이터셋마다 후보의 성격이 다르면 한 값으로
  나눈 N이 어떤 데이터셋에서는 너무 크고 어떤 데이터셋에서는 너무 작다.
  데이터셋별로 재는 것이 맞지만, 그러려면 데이터셋마다 예비 평가를 해야 한다.
- **idle 문턱 60초에 실측 근거가 없다.**
