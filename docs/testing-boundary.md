# 무엇을 검사가 잡고 무엇을 못 잡는가

> docs/24 B. **검사 수가 늘었다는 것은 완료 근거가 아니다**(24번이 그렇게
> 적었다). 무엇을 실제로 재고 무엇을 못 재는지를 적어 둔다.

**2026-09-09 기준.** 검사 총 **416건**.

이 수는 당시 기록이다. 최신 실행 결과는 CI 또는 실제 테스트 로그로 확인한다. [25번 계획 R1~R6](25-advancement-roadmap.md)의 화면 비동기 저장·복원 검사는 아직 후속 작업이며, 아래 순수 함수 검사에 포함된 것으로 간주하지 않는다.

## 세 층

| 층 | 수 | 무엇을 재는가 | GPU |
|---|---|---|---|
| 프론트 (vitest) | 84 | 키·판정 저장·CSV·필터의 순수 로직 + **실제 React 화면의 비동기 흐름**(R1) | 불필요 |
| 백엔드 (pytest) | 179 | API 계약, 경로 규칙, 서브프로세스 경계 | 불필요 |
| **실험 (pytest)** | **153** | **오류 주입(정답지)과 진단 규칙** | **불필요** |

세 층 다 **CI에서 매 push마다 돈다**(2026-09-08부터 — 실험 층은 그전까지 한
번도 안 돌았다).

## 실험 층이 왜 중요한가

`error_injector`는 **이 프로젝트 모든 수치의 정답지를 만드는 코드**다.
`apply_width`가 틀리면 `width_m30` 조건이 우리가 생각하는 것과 다른 것을
재고, 그 위에 쌓은 절 54개가 전부 흔들린다.

`label_diagnosis`는 진단 규칙 자체다 — 심각도 계산, 유형 판정, 재검수 순서,
바닥 식(docs/21 BB).

**둘 다 순수 계산이라 GPU가 필요 없다.** 대회 때부터 검사가 있었는데
`experiment/requirements.txt`에 torch가 들어 있어서 CI에 못 넣고 있었다.
무거운 것을 뺀 `requirements-ci.txt`로 갈랐고, **최소성은 빈 가상환경에서
실제로 확인했다**(pytest·pillow·pyyaml·python-dotenv만으로 66건 통과).

## 가짜와 진짜의 경계

**진단 서브프로세스 경계는 가짜로 검사한다.**
`backend/tests/fake_experiment.py`가 자리표시자 가중치와 **torch 없는 가짜
스크립트**를 만든다. 그래서 CI에서도 인자·작업 디렉터리·환경변수·리턴코드·
결과 JSON 모양까지 실제로 검사된다.

**추론 자체는 검사하지 않는다.** GPU가 필요하고 CI에서 못 한다.

| | 검사가 보는가 |
|---|---|
| 어떤 자를 고르는가, 그 자가 있는가 | **본다** |
| 스크립트를 어떤 인자·환경으로 부르는가 | **본다** |
| 결과 JSON의 모양과 필드 | **본다** |
| 업로드 경로가 백엔드와 스크립트에서 같은가 | **본다** |
| **모델이 실제로 무엇을 예측하는가** | **못 본다** |
| **진단 정밀도 수치** | **못 본다** |

**그래서 "검사 통과"는 "수치가 맞다"가 아니다.** 수치는 GPU에서 실제로 돌린
산출물로만 말할 수 있고, 그 대응표가
[current-evidence.md](./current-evidence.md)다.

## 검사가 규칙을 지키는 방식 — 수치 대신 규칙을 고정한다

GPU 수치를 CI에서 못 재는 대신, **그 수치를 만든 규칙이 조용히 뒤집히는 것**을
막는다. 실제로 그런 검사들이다.

| 검사 | 무엇이 뒤집히면 잡는가 |
|---|---|
| `test_review_order.py` | 계통적 유형 우선 규칙(docs/21 AN)이 사라지면 |
| 같은 파일 | 순서 근거·위험 판정이 화면에 안 나가면 |
| 같은 파일 | **측정 스크립트가 기준선을 제품 코드에서 물려받으면**(docs/21 AT·AU) |
| `test_uploads_dir_agreement.py` | 업로드 경로를 다시 박아 넣으면 |
| `experiment/tests/` | 좌표 변형·진단 규칙이 달라지면 |

**세 번째 줄이 특히 그렇다.** 그 실수를 이틀 새 두 번 했고, 적어두는 것으로는
안 막혀서 검사로 박았다.

## 아직 검사가 없는 것

- **`compare_keep_ratio.py`·`analyze_*.py` 같은 분석 스크립트.** CSV·JSON만
  읽으므로 순수한데 검사가 없다. (`run_manifest.py`와 `evaluation/`은

  규칙이 코드와 맞는지는 보지만, 그 규칙이 실데이터에서 쓸 만한지는 못 본다.
- **부트스트랩 구간의 통계적 성질을 안 봤다.** 재표집 단위와 짝지음이 맞는지는
  검사하지만, 그 구간이 실제로 95%를 덮는지(coverage)는 모의실험으로 확인하지
  않았다.
- ~~**누락 객체의 `unique_error_id`를 누가 어떻게 정하는지 아직 없다.**~~
  2026-09-09에 생산 경로를 만들었다 — 가림 판정 화면이 이미지 안에서 `M{n}`을
  정하고 서버가 이미지를 붙인다(docs/evaluation-adjudication-design.md).
  **그래도 판정자는 개발자다** — 아래 "무엇이 아직 아닌가"를 볼 것.
- **Δ와 N이 `TBD`다.** 계산은 되지만 **성공·실패 판정은 안 나온다**(`미정`). 잘못 세면 결론이 바뀐다 — 실제로 AV의 표를
  잘못 셌던 적이 있다(docs/21 AY).
- **`check_dataset_overlap.py`.** 성능은 실측했지만(docs/24 C1) 검사는 없다.
- **다른 화면.** `ReviewQueue`와 `BlindAdjudication`은 실제 컴포넌트로
  검사하지만(jsdom + Testing Library) `DatasetUpload`·`RulerCard`·`MethodCard`는
  아직 순수 함수와 눈으로 본 것뿐이다.

## 가림 판정이 아직 아닌 것

2026-09-09에 만든 것은 **판정을 기록할 길**이다. 다음은 여전히 아니다.

| 만든 것 | 아직 아닌 것 |
|---|---|
| 방법·점수·순위·세부 유형을 가린 화면 | **판정자가 개발자다.** 독립된 사람이 정답을 확정한 것이 아니다 |
| 후보를 얼리고 판정을 저장하는 경로 | **실제 판정 데이터가 없다.** 한 번도 돌리지 않았다 |
| 집계로 넣는 어댑터 | **누락 층에는 비교군이 없다.** 기술 통계만 나온다 |
| 단순 불일치 기준선(기존 라벨) | **한 번도 실제 데이터에서 돌리지 않았다.** 손계산 예제로만 확인했다 |
| 겹친 누락 후보를 한 오류로 잇는 기능 | 판정자가 **옳게 이었는지**는 검사가 못 본다 |

**네 가지를 갈라 읽어야 한다.**

| | 지금 상태 |
|---|---|
| 기존 라벨 후보의 **조건부 재정렬 효과** | 잴 수 있는 길이 생겼다. **안 쟀다** |
| 누락 후보의 **기술 통계** | 낼 수 있다. **안 냈다** |
| 후보 생성까지 포함한 **전체 제품 효과** | **경로가 없다.** 재정렬 효과를 이것으로 적지 않는다 |
| **외부 판정자 검증** | **없다.** 판정자는 개발자다 |

## 작업 시간 계측이 아직 아닌 것

2026-09-09에 계측 도구를 만들고 개발용 dry pilot을 돌렸다. **그 숫자는 사람의
검수 시간이 아니다.**

| 잰 것 | 무엇이 아닌가 |
|---|---|
| 후보당 P75 활동 시간 | **자동 클릭으로 나온 값이다.** 사람이 박스를 들여다본 시간이 아니다 |
| 세션·저장 실패·보류 수 | 흐름이 기록되는지 확인한 것 |
| N 공식 | 입력(`D`·`T`·실제 P75)이 **셋 다 없다** |

### 첫 파일럿은 판정이 불가능한 화면이었다 (2026-09-09 정정)

`make_timing_pilot.py`가 **1픽셀 회색 PNG를 늘려 쓰고 박스도 난수**로 만들었다.
그 화면에서는 라벨이 객체를 잘 감쌌는지, 지목된 자리에 객체가 있는지 알 수 없다.
**전부 "모르겠다"를 누르는 것은 클릭 시간을 재는 것이지 판정 시간이 아니다.**

지금은 개발 데이터의 실제 이미지를 쓰고, 후보는 `error_injector.py`로 실제
라벨에 오류를 주입해 만든다. 화면은 후보 박스(빨강)와 이미 붙어 있는 라벨
(파랑)을 구분해 그리고 클래스를 보여준다.

**후보는 AIDA의 예측이 아니다.** 자를 돌리지 않으므로 여기서 나오는 것은
판정 시간뿐이고, AIDA가 기준선보다 나은지와는 아무 관계가 없다.

자동 클릭 시간이 N으로 흘러가지 못하게 `implausible_for_human_judging`으로
막는다(후보당 중앙값 2초 미만, 보류 90% 초과 등). **넘겼다고 사람이 한 것이
증명되지는 않는다 — 못 한 것만 걸러낸다.**

### 속도로는 외부 도움을 알 수 없다 (timing1이 증거)

timing1은 후보당 중앙값 5.27초, 보류 0%로 **자동 클릭 검사를 전부 통과했지만**
판정자가 화면을 외부 도구에 보내 도움을 받았다. **그 도구에서 들여다본 시간은
이 탭의 활동 시간에 안 들어간다** — 탭이 숨은 동안을 빼도록 만들어 두었기
때문이다.

그래서 `judging_mode`를 **밖에서 적는다**(`pilot_meta.json`). `unaided_human`만
계획값을 내고, 적혀 있지 않으면 **"안 받았다"로 읽지 않는다.**

| 파일럿 | judging_mode | 결과 | 쓰임 |
|---|---|---|---|
| `timing1` | `assisted_rehearsal` | 24건, 한 세션 | **N 제외** — 외부 도움 |
| `timing2` | `unaided_human` | 24건, 한 세션 | **N 제외** — 재표집할 세션 하나 |
| `timing3a/b/c` | `unaided_human` | 24건, 세 세션, `timing_usable=True` | **하한으로만** — 주입 후보 |
| `timing4` | `unaided_human` | 47건, 세 세션, `actual_diagnosis` | **지속 판정 자료 없음** |

**timing4로도 N을 못 정한다.** 이유가 바뀌었다 — 후보는 이제 실제 진단
결과라 하한 문제는 풀렸지만, **네 파일럿 모두 8~24건짜리 짧은 묶음**이고 가장
긴 세션이 16건·1분 남짓이다. 1분짜리 집중을 1시간으로 늘려도 같은 속도가
유지되는지는 **재 본 적이 없다.** `s_plan = 3.58초`로 나누면 3시간·3데이터셋에
N=1005가 나오는데, 그 양을 같은 속도로 볼 수 있다는 근거가 없다.

**anchor가 네 번 반복해 말한 것:** 명백한 오류는 88%(45/51) 잡는데 **정상
라벨은 72%(21/29)만 그냥 둔다.** 판정자가 오탐 쪽으로 기운다. 실제 평가에서
`hit`이 부풀어 **절대 정밀도가 올라간다** — 두 방법의 차이는 같은 판정을 쓰니
덜 휘지만, 이 판정으로 "정밀도 94%" 같은 절대 수치를 만들면 안 된다.

**timing3의 `s_plan = 3.05초`는 하한이다.** 후보가 주입한 오류(크고 세 종류뿐)
이고 같은 과제를 세 번째 한 연습 효과가 있다(10.5 → 4.6 → 2.75초). 실제
후보는 더 미묘해 더 오래 걸린다.

`N = (T/D)/s_plan`이라 **하한을 넣으면 N이 과대해진다** — 보수적으로 잡으려던
시간 상한이 오히려 깨진다. 그래서 `candidate_source: injected_synthetic`을
적고, 안전계수를 명시하기 전에는 N을 내지 않는다.

timing1에서 또 하나 잡혔다. **온전한 세션 수만 세느라** 열고 닫기만 한 세션이
표본에 들어갔고, 재표집할 세션이 하나뿐인데 "95% 상한"이 평균과 똑같이 나왔다.
지금은 **판정이 든 세션 수**를 센다.

**dry pilot 값으로 N을 정하지 않는다.** 그것으로 정하면 사람이 클릭 속도로
검수한다고 가정하는 셈이다. 코드도 그렇게 막는다 — `timing_usable`이 거짓이면
`insufficient_pilot_data`를 돌려주고 숫자를 만들지 않는다.

**두 세션은 같은 판정자의 반복 작업 블록이지 독립 사용자 표본이 아니다.**
세션 부트스트랩 상한은 **이 개발자의 운영시간 계획용 휴리스틱**이고, 외부
사용자 속도나 모집단 일반화의 근거가 아니다. 세션이 독립 관측이라는 가정 자체가
약하다 — 같은 사람이 같은 날 연달아 한 작업이라 뒤 세션은 앞에 익숙해진 상태다.

**계획값은 P75가 아니라 평균의 부트스트랩 상한(`s_plan`)이다.** 처음에는 "평균을
쓰면 절반의 경우 상한을 넘는다"고 적었는데 **그 설명은 성립하지 않는다** — 총
시간은 개별 후보의 P75가 아니라 평균·분산·세션 상관에 좌우된다. `s_plan`도
확률 보장이 아니라 보수적 참고값이다.

계측 규칙 자체(무엇을 빼고 무엇을 남기는가)는 손계산 timeline과 대조해
고정했다(`experiment/tests/test_evaluation_activity.py`). **규칙이 맞는지는
보지만, 그 규칙으로 잰 값이 대표값인지는 못 본다.**

### 기록 유실에 대해 아는 것과 모르는 것

| | |
|---|---|
| **막는다** | 재전송 중복(`event_id`), 모르는 이벤트, 형식 오류, 얼린 목록 밖의 후보, 부분 저장 |
| **드러낸다** | 빠진 순번, 끊긴 세션, 시계 역행 — `timing_usable`이 거짓이 된다 |
| **못 막는다** | `sendBeacon`이 실패하고 그 뒤 브라우저 저장소까지 비면 그 구간은 **복구할 수 없다.** 순번 구멍으로 드러날 뿐이다 |
| **안 봤다** | 모바일 브라우저의 종료 동작, 사생활 보호 모드의 저장소 정책 |

가림 범위도 정확히 적는다. **가리는 것**은 방법·점수·원래 순위·세부 의심
유형이고, **못 가리는 것**은 기존 라벨 검수인지 누락 객체 검수인지다. 판정
작업 자체가 달라 숨기면 판정할 수 없다.

브라우저에서 한 번 흐름을 확인했다(2026-09-09, 임시 데이터셋 4후보). 후보를
얼리고 → 가림 목록을 받고 → 판정하고 → 겹친 누락 둘을 `M1`로 잇고 →
내보내기를 집계 모듈에 넣어 **고유 오류 2개**가 나오는 것까지 봤다. 임시
데이터셋은 확인 뒤 지웠다. **이것은 도구가 도는지 본 것이지 성능을 잰 것이
아니다.**

## 실제 브라우저는 아니다 — jsdom의 경계 (docs/25 R6)

2026-09-09부터 `ReviewQueue`의 흐름 전체를 실제 컴포넌트로 검사한다 —
**열기 → 연속 판정 → 저장 실패 → 재시도 → 새로고침 → CSV.** 지연 응답과
네트워크 실패를 검사가 직접 쥐고 흔든다.

`BlindAdjudication`도 같은 방식으로 검사한다 — 가림, 판정 저장, 취소, 저장
실패와 재시도, 누락 객체 잇기, 묶음 해시 불일치, 파일 손상.

**그래도 jsdom은 브라우저가 아니다.**

| | 검사가 보는가 |
|---|---|
| 상태 갱신 순서, 비동기 경쟁 | **본다** |
| 어떤 요청을 어떤 순서로 보내는가 | **본다** |
| 실패·지연에 화면이 무엇을 말하는가 | **본다** |
| `localStorage` 읽기·쓰기 | **본다**(jsdom 구현) |
| **실제 렌더링·레이아웃·CSS** | **못 본다** |
| **브라우저의 저장 용량 정책, 사생활 보호 모드** | **못 본다** |
| **여러 탭의 진짜 `storage` 이벤트** | **못 본다** — 흉내만 낸다 |
| **실제 네트워크·CORS·타임아웃** | **못 본다** |

레이아웃을 못 보는 것이 실제로 걸렸다. 가림 판정 화면에서 저장 문구가 판정
버튼 **위**에 있어, 판정할 때마다 버튼이 아래로 밀렸다 — 연달아 누르면 엉뚱한
버튼을 누른다. **jsdom 검사는 이것을 못 잡았고 브라우저에서 잡았다.** 고친 뒤에는
밀림을 막는 문서 순서(상태 문구가 버튼보다 뒤)를 검사로 고정했다.

**계획(docs/25 R6)이 요구한 "브라우저 통합 검사"는 아직 아니다.** Playwright 같은
것을 넣으려면 CI에서 브라우저를 내려받고 백엔드까지 띄워야 한다 — 지금 한 것과
값이 겹치는 부분이 크고 비용이 다르다. **미완으로 남긴다.**

화면을 바꿀 때는 여전히 브라우저에서 직접 확인한다.
