# timing5 — 지속 판정 파일럿 (사전 등록)

> **데이터를 만들기 전에 쓴다.** 성공 기준과 분석법을 결과 열람 전에 고정하는
> 것이 이 문서의 전부다. 후보도 판정도 아직 없다.
>
> 작성 2026-09-12.

## 무엇을 묻는가

**후보당 판정 시간과 판정 품질이 오래 이어갈 때도 유지되는가.**

timing1~4는 전부 8~24건짜리 짧은 묶음이었고 **가장 긴 연속 판정이 16건·약
1분**이다. 거기서 나온 `s_plan = 3.58초`를 3시간으로 나누면 데이터셋당
N=1005가 나오는데, **1분짜리 집중을 1시간으로 늘려도 같은 속도가 유지되는지는
재 본 적이 없다.**

| 아는 것 | 모르는 것 |
|---|---|
| 16건을 3.5초씩 판정한다 | 100번째 후보에서도 그런가 |
| 세션 사이에 쉬면 회복된다 | 쉬지 않고 이어가면 어떻게 되는가 |
| 정상 라벨에 오탐이 있다 | 지치면 그 오탐이 늘어나는가 |

## 자료 — 실행 전에 고정한다

| 항목 | 값 |
|---|---|
| 후보 출처 | `actual_diagnosis` (자를 돌려 나온 실제 후보) |
| 실제 후보 | **100건** |
| anchor | **20건** (정상 10 · 명백한 오류 10) |
| 전체 | **120건** |
| 표집 시드 | **`5203`** |
| 판정 방식 | `unaided_human` |
| 데이터셋 id | `ffffffffff07` / 평가 id `timing5` |

**anchor 비율을 20건으로 올린 이유**는 구간마다 anchor가 들어가야 하기 때문이다.
timing4는 48건에 8건이라 구간을 나누면 구간당 2건 남짓이었다. 120건에 20건이면
25건 구간마다 약 4건이다 — **여전히 적다.** 구간별 anchor 수치는 경향을 보는
것이지 검정이 아니다.

### 빼는 것

1. **timing1~4가 쓴 이미지** (판정자가 이미 봤다)
2. 자의 학습 라벨(`labels_gt/train`)에 있는 stem
3. **`images/train`에도 사본이 있는 것**

2·3은 자가 본 적 있는 프레임을 걸러내려는 것이다. 논리적 분할과 파일이 놓인
자리가 달라 **둘 다** 봐야 한다.

**최종 평가 데이터와 사용자 데이터셋 5개는 쓰지 않는다.**

### 남기는 것

`pilot_manifest.json`에 사용 이미지 목록, 가중치 SHA-256, 코드 커밋, 설정,
생성 시각, **후보 목록 해시**를 적는다. 표집 전후 구성 비율도 함께.

## 수행 — 실행 전에 고정한다

1. **한 번의 연속 판정**으로 한다. 중간에 탭을 닫지 않는다.
   timing1~4와 반대다 — 여기서는 **이어서 하는 것이 측정 대상**이다.
2. idle · 탭 비활성 · 대기 시간은 **기존 규칙대로 제외**한다
   (60초 문턱, `visibility`/`focus`, `save`/`queue_load` 대기).
3. 다른 도구에 **개별 판정을 묻지 않는다.**
4. 애매하면 `모르겠다`.
5. anchor 정답표는 **완료 전 열지 않는다.**

### 중단 규칙 — **미리 정한다**

- **피로하거나 평소 작업 속도가 아니게 되면 멈춘다.** 억지로 채우지 않는다.
- 멈춘 지점과 이유를 기록한다. **중단 자체가 결과다** — "120건을 못 이어간다"는
  것도 이 파일럿이 답하려는 질문의 답이다.
- 저장 실패가 반복되면 멈춘다(도구 문제).

## 분석 단위 — **실행 전에 고정한다**

판정한 순서대로 **25건씩** 끊는다.

```
1~25 / 26~50 / 51~75 / 76~100 / 101~120
```

마지막 구간은 20건이다. **끝까지 못 갔으면 완성된 구간까지만 본다** — 남은
반쪽 구간은 보고하되 비교에 쓰지 않는다.

구간을 **판정 순서**로 끊는 이유는 피로가 시간이 아니라 작업량에 따라 오기
때문이다. 화면을 열어 둔 시간이 아니라 **몇 번째 후보인가**가 기준이다.

### 구간마다 보고할 것

| | |
|---|---|
| 후보당 활동 시간 | 평균 · 중앙값 |
| `hold` 수와 비율 | 판단을 미루는 빈도가 느는가 |
| anchor 정상 유지 | 멀쩡한 라벨을 그냥 두는가 |
| anchor 오류 탐지 | 명백한 오류를 잡는가 |
| 판정 수 | 구간이 실제로 찼는가 |

**첫 구간 대 마지막 구간**을 반드시 나란히 적는다.

## `s_plan`을 어떻게 낼 것인가 — **임의 문턱을 만들지 않는다**

지금까지는 **세션**을 재표집 단위로 썼다. 지속 판정은 세션이 하나이므로 그
방식을 못 쓴다.

**재표집 단위를 구간으로 바꾼다.**

```
s_plan = 후보당 평균 시간의 부트스트랩 95% 상한 (구간 단위 재표집)
```

이 규칙이 좋은 점은 **"속도가 몇 % 이상 변하면 실패"라는 임의 문턱이 필요
없다**는 것이다.

- 후반이 느려지면(피로) 느린 구간이 상한을 밀어 올린다 → 보수적
- 후반이 빨라지면(숙련) 초반 느린 구간이 상한에 남는다 → 보수적

어느 쪽이든 **변동이 클수록 계획값이 커진다.** 문턱 없이 변동이 값에 반영된다.

**그래도 확률 보장은 아니다.** 구간이 4~5개뿐이라 재표집이 만드는 분포가 거칠고,
부트스트랩이 가정하는 "구간이 서로 교환 가능하다"는 것도 피로가 있으면 틀린다.
**보수적 참고값**으로만 쓴다.

### 표본 요건

`timing_usable`의 기존 조건에 더해:

- **완성된 구간이 3개 이상**이어야 `s_plan`을 낸다. 둘이면 재표집 결과가
  셋뿐이라 구간이 아무것도 말하지 않는다(timing2에서 겪은 것과 같은 문제).

이 값도 **근거가 약한 운영 기준**이다.

## N을 어떻게 정할 것인가 — **1시간 외삽을 하지 않는다**

지속 판정이 100건이어도 **1000건을 이어서 할 수 있다는 근거는 안 된다.**
그래서 나눗셈 한 번으로 N을 정하지 않는다.

```
관측한 지속 단위 = 이 파일럿에서 실제로 끊김 없이 판정한 건수 (B)
블록당 소요 = B × s_plan
블록 수      = floor(T / D / (B × s_plan))
N            = 블록 수 × B
```

**외삽하는 것은 "블록을 반복한다"뿐이다.** "한 시간을 쉬지 않고 같은 속도로
간다"가 아니다. 블록 사이에는 쉰다 — timing1~4에서 세션 사이 회복은 관측했다.

산술적으로는 같은 나눗셈이지만 **가정이 다르다.** 그리고 B가 관측값이라
"블록이 몇 개인가"가 명시적으로 드러난다 — 20블록이 필요하다면 그것이
현실적인지 사람이 보고 판단할 수 있다.

## 품질 기준은 **여전히 만들지 않는다**

"정상 anchor 오탐이 몇 건까지 괜찮은가"에 근거가 없다. 결과를 보고 정하면
사후 설명이다.

- 보고서는 구간별 anchor 결과를 **그대로 적는다.**
- 상태는 `quality_threshold_not_preregistered`로 남는다.
- **N 출력은 `--reviewed` 뒤에만** 나온다. 사람이 구간별 속도·품질 변화를
  보고 받아들였다는 표시다.

**이 파일럿이 품질 기준을 만들어 주지 않는다.** 만드는 것은 사람이거나, 외부
판정자와의 합의 정답이다.

## 이 파일럿이 말하지 않는 것

- **판정자가 한 명이고 이미 네 차례 연습했다.** 숙련 운영자의 지속력이지
  신규 사용자의 것이 아니다.
- **하루 중 언제 했는가**를 통제하지 않는다. 피곤한 저녁과 아침이 다를 수 있다.
- **한 번의 지속 판정**이다. 같은 사람이 다른 날 하면 다를 수 있고, 그 변동은
  안 잰다.
- 개발 데이터(KITTI 주행·단일 클래스)의 후보가 고객 데이터를 대표한다는 보장이
  없다.
- **실제 후보의 판정 정확도는 모른다.** 정답이 없고 외부 판정자도 없다.
- anchor는 주입한 오류라 실제 후보의 난이도를 말하지 않는다.
